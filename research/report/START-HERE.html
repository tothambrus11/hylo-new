Hylo type checker: findings, fixes and open questions

This package describes a study of the type checker of hylo-new: nine soundness problems of the existing implementation with a fix for each, two kinds of valid generic programs that it rejects, and a set of techniques that make it 4.5× faster on the standard library. Several of the fixes rest on a reading of the language that only its designer can confirm. Those readings are stated here as eighteen questions, each with a small program.

This page is the entry point. It takes about twenty minutes to read; everything else in the archive is supporting detail.

What is asked

  1. Are the nine findings defects? Each has a program of a dozen lines in reproducers/ that can be checked with an unmodified compiler. Eight of them should be uncontroversial. The seventh depends on questions 1 and 2.
  2. Answers to the questions, where there is one. Four decide most: 1 and 2 (are conformances coherent across equal types), 8 (which witness a requirement gets), and 11 (the status of the bound on derivations). A short answer to each is enough to say which parts of the fixes should be relaxed, tightened or removed.
  3. A judgement on two mechanisms that are larger than a fix usually is: computing the types of extensions and givens in rounds, so that results do not depend on declaration order (problem 5), and proving requirements that mention an associated type of another requirement. Together they are about 1,100 lines and the least reviewed part of the work.

Provenance and confidence

The implementation, the test programs and the documents were produced with an AI coding agent (Claude), directed by the sender. No part has been reviewed by a second person, and no argument is mechanized. What supports the results is the following.

  • Every change is behind a flag that is off by default. Without flags, the patched compiler is the existing implementation.
  • Unchanged output on the test suite. A dump of every inferred type, name binding, conformance table, diagnostic and elaborated witness is identical to that of the existing implementation on the 192 compiler tests and 24 workloads, for the result-preserving techniques and also with every fix enabled. The fixes change results only on programs that exercise the defects, and the test suite has none.
  • A self-checking mode re-does the work that each technique avoids and compares. It reports no violation on 1,651 programs.
  • Independent tests. A reference resolver written from the compiler's tests, compared on 21,500 generated queries, and 15,206 metamorphic variants of 760 programs. They found problems 6, 7 and 9.
  • Adversarial review. Each design and each new mechanism was attacked with programs written to break it, about 550 in all. The attacks found more than twenty defects in first implementations, six of them wrong acceptances; all are fixed and kept as tests. The last round of attacks was not judged by a second reviewer.

The arguments for correctness are informal. For problems 5 to 9 and for dependent requirements, the attacks found errors in arguments that had seemed complete, and nothing guarantees that they found the last one. Hylo has little generic code so far: the standard library has no equality constraint and no associated type in a signature, so the mechanisms that concern them are exercised only by programs written for this study and by four patterns translated from the Swift and Rust standard libraries.

Findings in the existing implementation

Problems 1, 6, 7, 8 and 9 let an ill-typed program through: in the reproducers of 6 and 9 a value of one concrete type is passed where another is expected, and in that of 8 a method is called on a type that does not have it. Problem 4 is a crash, problem 5 is two verdicts for one program, and problems 2 and 3 are costs that become failures on slightly larger programs. "Existing" is the unpatched compiler; "With the fixes" is the recommended configuration.

Questions on the language

Each entry gives the question, a program, what the type checker does with it today, what the fixes assume, and what would change with the other answer. The programs are in questions/; questions/README.md has the same list as text, convenient for answering inline. Questions 3, 4, 7, 10, 15 and 16 describe behaviour that this work leaves unchanged; they are listed because every technique had to reproduce it, and a different answer would simplify the implementation.

Conformances and equalities

1. Are conformances coherent across equal types? decides most

With T == U, T is P and U is P, are the two requirements the same witness, so that T.X and U.X are the same type?

questions/q01-coherence.hylo
trait P { type X }
fun check<T>(x: T) {}
fun f0<T, U where T == U, T is P, U is P>(x: U.X) {
  check<T.X>(x)
}
Today
Rejected, by the existing implementation and by the fixes. This is the compiler's negative test associated-type-inequality.
Assumed
No: two requirements are two witnesses, which may define X differently. Every fix follows this reading.
Otherwise
If conformances are coherent, problem 7 below is not a defect, types can be rewritten to a representative of their equality class (rejected here as unsafe, because a conformance is selected by the way a type is written), and the restrictions of abstractstrict can be lifted.

2. Inside a trait, is Self.X equal to T.X when T == Self and T is P? decides most

T is P is a second requirement, which the caller satisfies independently of the witness that the trait stands for.

questions/q02a-self-projection.hylo
trait P {
  type X
  fun f<T where T == Self, T is P>(x: X) { check<T.X>(x) }
}
fun check<T>(x: T) {}
questions/q02b-self-projection-conversion.hylo
fun conv<A, B where A == B>(x: A) -> B { x }
fun check<T>(x: T) {}
trait P {
  type X
  fun cast<T, U where T == Self, T is P, T.X == U>(x: U) -> X { conv<U, X>(x) }
}
fun f<V, W where V == W, V is P, W is P>(v: V, x: W.X) {
  check<V.X>(v.cast<W, W.X>(x))
}
Today
q02a: accepted by the existing implementation, rejected by the fixes. q02b uses the rule to convert a W.X into a V.X under the where clause of question 1: the existing implementation exhausts memory on it; with the equality procedure alone it is accepted; with the fix it is rejected.
Assumed
No, for consistency with question 1: a selection through the trait's own witness equals only a selection through that same witness (abstractstrict). Eight test programs of the shape of q02a are rejected as a result.
Otherwise
If they are equal, the rule must be reconciled with question 1, since q02b performs exactly the conversion that the negative test forbids.

3. What do equalities between concrete types mean?

Does Box<T> == Box<U> give T == U? Is where T == A, T == B, for two distinct structs, an error where it is declared?

questions/q03a-injectivity.hylo
struct Box<X> { public memberwise init }
fun check<T>(x: T) {}
fun f<T, U where Box<T> == Box<U>>(x: T) { check<U>(x) }
questions/q03b-two-concrete-types.hylo
struct A { public memberwise init }
struct B { public memberwise init }
fun check<T>(x: T) {}
fun f<T where T == A, T == B>(x: A) { check<B>(x) }
Today
q03a is rejected: type constructors are not injective for equalities. q03b is accepted: in the body, an A is passed where a B is expected. No caller can satisfy the clause. Both behaviours are those of the existing implementation and are unchanged.
Assumed
Nothing is assumed; the equality procedure reproduces both behaviours.
Otherwise
Injectivity would be a new rule of the congruence closure. Rejecting q03b at the declaration would be a new check for clauses that equate two distinct nominal types.

4. Are the members of A available on a T when T == A?

Members of a trait are found through an equality; members of a struct, and its extensions, are not.

questions/q04a-struct-member-through-equality.hylo
struct A {
  public memberwise init
  fun foo() {}
}
fun f<T where T == A>(x: T) { x.foo() }
questions/q04b-trait-member-through-equality.hylo
trait P { fun p() }
fun f<T, U where T == U, U is P>(x: T) { x.p() }
Today
q04a is rejected ("type 'T' has no member 'foo'"), q04b is accepted. Unchanged.
Assumed
Nothing is assumed.
Otherwise
If struct members should be found, member lookup has to consult the equalities in scope.

5. How should a trait state an equality between its associated types?

Swift's Sequence has Iterator.Element == Element. In a survey of the Swift standard library, swift-collections and Rust's iterator library, 6% to 24% of the functions have an equality in scope, mostly through traits.

questions/q05-equality-in-trait.hylo
trait IteratorProtocol { type Element }
trait Sequence {
  type Element
  type Iterator
  given Iterator is IteratorProtocol
  given Iterator.Element == Element
}
fun need<A, B where A == B>() {}
fun f<S where S is Sequence>() { need<S.Iterator.Element, S.Element>() }
Today
A syntax error: "expected 'is'".
Assumed
Nothing is assumed; the feature does not exist.
Otherwise
An equality stated by a trait holds for every conforming type, so it is not ground. Two of the techniques (eqindex, coeset) rely on the equalities in scope being ground; they fall back to the general path otherwise and would need to be revisited.

6. Does anything depend on the shape of an equality proof?

The decision procedure builds the term of an equality proof differently from the search. On the compiler's tests, this is the only difference in the elaborated output (two files).

Today
No program: the question is about later phases.
Assumed
No: any proof term of the right type is as good as another.
Otherwise
If lowering, or a checker of derivations, needs a particular form, the procedure must build that form.

Requirements of a where clause

7. Is the order of requirements meant to be significant?

A requirement is an assumption for the requirements written after it, so reordering a clause changes how many steps a call needs.

questions/q07a-where-order.hylo
trait P {}
trait Q {}
struct A0 {}
struct A1 {}
struct A2 {}
struct A3 {}
struct C {}
struct S<T> {}
given A0 is P {}
given A1 is P {}
given A2 is P {}
given A3 is P {}
given <where A0 is P, A1 is P, A2 is P, A3 is P> => C is P {}
given <T where T is P> => S<T> is Q {}
fun f<where C is P, S<C> is Q>() {}
public fun main() { f() }
questions/q07b-where-order-swapped.hylo
trait P {}
trait Q {}
struct A0 {}
struct A1 {}
struct A2 {}
struct A3 {}
struct C {}
struct S<T> {}
given A0 is P {}
given A1 is P {}
given A2 is P {}
given A3 is P {}
given <where A0 is P, A1 is P, A2 is P, A3 is P> => C is P {}
given <T where T is P> => S<T> is Q {}
fun f<where S<C> is Q, C is P>() {}
public fun main() { f() }
Today
q07a is accepted (8 steps); q07b, the same program with the two requirements swapped, is rejected (12 steps, past the bound of question 11). Unchanged.
Assumed
The existing rule is kept.
Otherwise
If the order should not matter, the requirements must be assumptions for each other in both directions, or in neither. The experiment heightbound accepts both programs by changing the bound instead.

8. Which witness does a requirement get when another requirement mentions it? decides most

For where T is P, T.X is Q: is the witness of T is P the one that resolving it alone gives, or may the second requirement select among the conformances in scope?

questions/q08-which-witness.hylo
trait P { type X }
trait Q {}
struct A {}
struct B {}
struct C {}
given B is Q {}
given A is P { type X = B }
fun f<T where T is P, T.X is Q>() {}
public fun main() {
  given A is P { type X = C }
  f<A>()
}
Today
Rejected by both. The existing implementation rejects every call whose requirements mention an associated type of another requirement. The fix rejects this one because A is P alone resolves to the local conformance, for which A.X is C, and C is not Q.
Assumed
On its own: the requirement is resolved first, a tie is an ambiguity, and the dependent requirement is then proved for that witness (premcommit).
Otherwise
Solving the requirements together accepts q08 through the shadowed conformance of the module. Five programs of the test corpus differ between the two readings.

9. Is an associated type selected through a declared conformance equal to its definition?

In particular for a generic conformance, where the definition mentions the conformance's own parameters.

questions/q09a-generic-conformance-unsound.hylo
trait P { type X; fun get() -> X; fun put(x: X) }
struct A { public memberwise init }
struct C { public memberwise init }
given <T> => T is P {
  type X = T
  fun get() -> T { self }
  fun put(x: T) {}
}
fun q(a: A, c: C) { c.put(a.get()) }
questions/q09b-generic-conformance-valid.hylo
trait P { type X; fun get() -> X; fun put(x: X) }
struct A { public memberwise init }
given <T> => T is P {
  type X = T
  fun get() -> T { self }
  fun put(x: T) {}
}
fun check<T>(x: T) {}
fun q(a: A) { check<A>(a.get()) }
Today
q09a is accepted by the existing implementation: an A is passed where a C is expected. q09b, which is valid, is rejected by it. The fix reverses both.
Assumed
Yes: A.X through given <T> => T is P { type X = T } is A, with the arguments and the witnesses of the conformance substituted into the definition (assocsubst).
Otherwise
Probably uncontroversial. One related case has no diagnostic: a parameter of a conformance that neither its head nor its requirements determine (given <T, U> => Box<T> is P { type X = U }) yields a fresh type at each use. Should it be an error at the declaration?

Ranking and the bound on derivations

10. Is the ranking of derivations through equalities intended?

Which of two conformances wins depends on the side on which an equality is written, because penalties count pending requirements and a derivation that uses symmetry is longer.

questions/q10a-ranking.hylo
trait P {}
fun g<V where V is P>() {}
fun f<A, B, C where B is P, C is P, B == A, A == C>() { g<A>() }
questions/q10b-ranking-other-side.hylo
trait P {}
fun g<V where V is P>() {}
fun f<A, B, C where B is P, C is P, B == A, C == A>() { g<A>() }
Today
q10a (B == A, A == C) is accepted; q10b (B == A, C == A) is rejected as ambiguous. Of 800 generated goals with two symmetric derivations, 408 are accepted and 392 reported as ambiguous. Unchanged: the fixes reproduce the ranking exactly.
Assumed
The ranking is treated as part of the language, and every technique was required to preserve it.
Otherwise
If symmetric derivations should always be ambiguous (or never), the ranking can be defined on the equality classes, and the techniques no longer need to reproduce step counts.

11. Is the bound of ten steps part of the language? decides most

Does it bound the size of a derivation (all the givens used for a call) or its depth? Do the steps that prove equalities count? Is reaching it an error, or a silent failure after which another extension or overload is selected?

questions/q11a-bound-four.hylo
trait P {}
struct A {}
struct Pair<X, Y> {}
given A is P {}
given <X, Y where X is P, Y is P> => Pair<X, Y> is P {}
fun need<T where T is P>() {}
public fun main() { need<Pair<A, Pair<A, Pair<A, Pair<A, A>>>>>() }
questions/q11b-bound-five.hylo
trait P {}
struct A {}
struct Pair<X, Y> {}
given A is P {}
given <X, Y where X is P, Y is P> => Pair<X, Y> is P {}
fun need<T where T is P>() {}
public fun main() { need<Pair<A, Pair<A, Pair<A, Pair<A, Pair<A, A>>>>>>() }
questions/q11c-bound-selects-member.hylo
struct A0 { public memberwise init }
struct A1 { public memberwise init }
struct A2 { public memberwise init }
struct A3 { public memberwise init }
struct A4 { public memberwise init }
struct A5 { public memberwise init }
struct A6 { public memberwise init }
struct A7 { public memberwise init }
struct A8 { public memberwise init }
struct W<X0, X1, X2, X3, X4, X5, X6, X7, X8> { public memberwise init }
extension W<A0, A1, A2, A3, A4, A5, A6, A7, A8> { fun m() {} }
extension <X8> W<A0, A1, A2, A3, A4, A5, A6, A7, X8> { fun m() {} }
fun f<T0, T1, T2, T3, T4, T5, T6, T7, T8 where T0 == A0, T1 == A1, T2 == A2, T3 == A3, T4 == A4, T5 == A5, T6 == A6, T7 == A7, T8 == A8>(x: W<T0, T1, T2, T3, T4, T5, T6, T7, T8>) { x.m() }
Today
q11a (9 givens) is accepted. q11b (11 givens, valid) is rejected with "no coercion", without mention of the bound. In q11c two extensions apply, and proving so needs nine equalities for the first and eight for the second: the existing implementation exhausts memory; with the equality procedure alone the member of the second extension is called; in the recommended configuration, where equalities proved by the procedure are not counted, the member of the first is.
Assumed
The bound is kept as it is, on the size of a derivation, with silent failure. Equalities decided by the procedure are not counted (eqeager), which is the one intended change of behaviour among the performance techniques.
Otherwise
The experiment heightbound bounds the depth instead and accepts q11b and q07b. If reaching the bound were an error, q11c would have one meaning.

Declaration order

12. May the types of extensions and givens depend on each other?

Looking up the type that one extension extends can require the other extension, and conversely.

questions/q12-mutually-dependent-extensions.hylo
struct A { struct Inner {} }
extension A.Inner.Foo { type Inner = Bool }
extension A.Inner { type Foo = Int }
fun use(x: Int.Inner) {}
Today
The existing implementation accepts q12 in 12 of the 24 orders of its declarations. The fix accepts it in all 24: it computes these types in rounds until they are stable, and reports the declarations for which no stable reading is found.
Assumed
Yes, when the iteration reaches a stable reading (sigrounds).
Otherwise
A stricter rule, rejecting every such dependency, can be added as a check on the stable result. It would also remove the remaining unproved step in the argument that the overload techniques preserve results.

13. May a given be a candidate in its own initializer, and what is a given with an inferred type worth outside a function?

Today a given is hidden while its own type is computed, and a given without a written type is typed on demand, inside the first resolution that meets it.

questions/q13a-given-in-own-initializer.hylo
struct A { public memberwise init }
fun make<where let u: A>() -> A { u }
given let other: A = A()
given let w = make()
public fun main() {}
questions/q13b-given-initialized-with-itself.hylo
struct A { public memberwise init }
fun make<where let u: A>() -> A { u }
given let w: A = make()
public fun main() {}
questions/q13c-inferred-given-order.hylo
struct A { public memberwise init }
let s = A()
given let g = s
fun need<where let u: A>() {}
public fun main() { need() }
Today
q13a is accepted: w is initialized with other. q13b is accepted by every configuration: a given with a written type is the only candidate for its own initializer. q13c is accepted in 15 of the 24 orders of its declarations, by the existing implementation and by the fixes alike.
Assumed
The fix for declaration order covers declarations whose type is written; q13c is not fixed.
Otherwise
Four options were tried and none is adopted (experiments/inferred-givens/README.md). The simplest is a rule: a given declared outside a function must have a written type. The most complete one makes q13c independent of the order but rejects q13a, because the given then sees itself.

14. Is the order of givens in a function body meant to matter, and may a where clause name a declaration of the body it governs?

Givens declared in a body are visible in the whole body, before their declaration.

questions/q14a-givens-in-body.hylo
trait P { type E }
trait Q { type F }
struct A {}
struct C {}
given A is P { type E = Int }
given A is Q { type F = Int }
extension Int { type T = A }
extension Bool { type T = C }
fun h() {
  given A.F.T is P { type E = Bool }
  given A.E.T is Q { type F = Bool }
  let z: A.E = true
}
questions/q14b-givens-in-body-swapped.hylo
trait P { type E }
trait Q { type F }
struct A {}
struct C {}
given A is P { type E = Int }
given A is Q { type F = Int }
extension Int { type T = A }
extension Bool { type T = C }
fun h() {
  given A.E.T is Q { type F = Bool }
  given A.F.T is P { type E = Bool }
  let z: A.E = true
}
questions/q14c-where-clause-uses-body.hylo
trait P { type X }
trait Q {}
fun f<T where T is P, LA is Q>() {
  type LA = T.X
}
Today
The existing implementation rejects q14a and accepts q14b, which differs in the order of two local givens. The fix rejects both: each given can shadow the top-level one that the other needs, and no stable reading is found. q14c is accepted by both.
Assumed
Local givens are treated like top-level ones, so their order does not matter.
Otherwise
If the order in a body is meant to matter, local givens must be excluded from the rounds.

Overload resolution

15. Is the nested ranking of overloads intended?

Only the outermost overloaded name of a statement is ranked across all combinations; the inner ones are ranked inside each choice of the outer one.

questions/q15-nested-ranking.hylo
struct X { public memberwise init }
struct Y { public memberwise init }
struct S {
  public memberwise init
  public static fun a() -> Y { Y() }
  public static fun b() -> X { X() }
}
fun k<V>(x: V, y: V) -> V { x }
fun takeX(x: X) {}
fun takeY(y: Y) {}
fun main() {
  extension S {
    static fun a() -> X { X() }
    static fun b() -> Y { Y() }
  }
  let p = k(S.a(), S.b())
  takeX(p)
  let q = k(S.b(), S.a())
  takeY(q)
}
Today
Accepted: k(S.a(), S.b()) is an X and k(S.b(), S.a()) is a Y. Unchanged.
Assumed
The existing ranking is preserved exactly.
Otherwise
A ranking of whole combinations would be independent of the order of arguments.

16. Should a solution with more errors than the best one stay viable?

A preferred candidate with an error can win over one whose only diagnostic is a nested ambiguity.

questions/q16-erroneous-candidate-wins.hylo
struct A {
  public memberwise init
  public fun n() -> A { A() }
  public fun n() -> A { A() }
}
struct B {
  public memberwise init
  public fun n() -> B { B() }
}
struct S {
  public memberwise init
  public static fun f() -> A { A() }
}
fun takeA(x: A) {}
public fun main() {
  extension S { static fun f() -> B { B() } }
  takeA(S.f().n())
}
Today
Rejected with the error of the preferred candidate ("cannot pass value of type 'B' to parameter 'A'"). Unchanged.
Assumed
The existing behaviour is preserved exactly.
Otherwise
If only the candidates with the fewest diagnostics stayed viable, more of the search could be cut once a clean solution is known.

17. Should a member and the trait requirement that it implements be two candidates?

For a concrete receiver they denote the same function.

questions/q17-member-and-requirement.hylo
public fun main() {
  let a = 1
  let b = a + a + a + a + a + a + a + a + a + a + a + a + a + a + a
}
Today
Accepted. The existing solver makes 32,766 forks for 14 operators; with twins, which shares the search between two candidates of the same type, 14.
Assumed
Both candidates are kept, and the second reuses the result of the first.
Otherwise
If name resolution kept one candidate, the exponential cost would disappear at its source and twins would not be needed.

18. Are the diagnostics of an ill-typed statement part of the contract?

May an implementation report a different, smaller set of errors for a statement that has none of the solutions?

Today
No program: the question is about what must be preserved.
Assumed
Yes: an erroneous statement is solved by the existing search, so that its diagnostics are unchanged. The overload techniques therefore speed up well-typed statements only.
Otherwise
If the set of diagnostics may differ, erroneous statements can be made fast as well.

Type-checking time in milliseconds, one core. The full table, the contribution of each technique and an assessment of which ones are worth their complexity are in report.html.

  • On code without equality constraints, five simple techniques give the whole gain: indexing givens by the head constructor of their conclusion, skipping extensions that do not declare the requested name, and three constant-factor improvements. They are about 450 lines and leave every result unchanged.
  • On code with equality constraints, the gain comes from deciding equalities by congruence closure instead of by search, which is also what removes problems 1 to 3.
  • One technique is not recommended: an abstract model that refutes underivable goals. It removes an exponential cost on constructed programs, but made only one of 687 ill-typed variants of real programs more than ten times cheaper to reject, for about 600 lines.

What is not solved

  • Nested nominal types. A struct declared inside a generic conformance or a generic type is one type for all instances. This is unsound, exists in the unpatched compiler, and is outside the mechanisms studied.
  • Givens with an inferred type outside a function are still typed on demand, and the verdict can depend on declaration order (question 13).
  • The bound on derivations rejects valid programs (question 11).
  • Function values. A generic function whose signature mentions an associated type of its requirement can be called, but not passed as a value at a concrete type.
  • Associated types through a refinement are opaque: T.X selected through T is R, where R refines P, is not identified with the definition in the conformance to P.
  • Cost of dependent signatures. A chain of d extensions or givens whose types depend on each other costs d + 2 rounds over the whole module.

The complete list is in the section "Limitations" of report.html.

Reproducing the results

The existing behaviour, with an unmodified compiler

The programs of reproducers/ and questions/ are single files with the header of the compiler's tests (//! stage:typing no-std), so they can be copied into Tests/CompilerTests/positive or negative, or type-checked directly. The first lines of each file state the expected result. The results quoted on this page were obtained with the benchmark tool described below, run without flags, on commit 3ce4aa0 of main (4 November 2026); they were not re-run with hc.

The fixes

The patch series applies to the same commit:

git checkout -b type-checker-review 3ce4aa0
git apply --index patches/0000-base-harness-flags-and-first-techniques.diff
git commit -m "Benchmark harness, flags and first techniques"
git am patches/00*.patch
swift build -c release --product tc-bench

patches/all-in-one.diff is the same change as a single diff, for reading: 14 files, about 5,100 added lines, almost all in Typer.swift, Solver.swift and TypeStore.swift. Applied in this way, the series was checked to reproduce exactly the sources that produced the results.

tc-bench type-checks the files given to it and prints the diagnostics, their number and the time. The environment variable HYLO_TC_EXPERIMENTS selects the techniques:

# the existing implementation
.build/release/tc-bench reproducers/s6-generic-conformance.hylo

# the recommended configuration
export REC=index,typevec,symindex,traitindex,memberskip,twins,stackscan,coeset,reifymemo,occurs,fixsubst,eqsolve,eqmgu,arrowenv,budget,sigrounds,assocsubst,abstractstrict,hidecache,aliasargs,premsubst,premcommit,headsubst,dedup,eqindex,eqeager,cleanfirst,lookahead
HYLO_TC_EXPERIMENTS=$REC .build/release/tc-bench reproducers/s6-generic-conformance.hylo

# with the self-check, and with a trace of each completed resolution
HYLO_TC_EXPERIMENTS=$REC,selfcheck,trace .build/release/tc-bench reproducers/c2-collection.hylo

patches/README.md lists what each patch contains and which flags depend on each other. reproducers/observed.txt and questions/observed.txt hold the output of both configurations on every program.
