Hylo Type-Checker Optimizations

Implicit resolution, the search for a derivation of a constraint such as T is P from the givens in scope, dominates the running time of Hylo's type checker. This report presents techniques that reduce its cost, the soundness problems of the existing implementation that the work exposed, and fixes for ordinary generic programs that the existing implementation rejects.

The work has three parts:

  • performance: restricting the candidate givens to those that can match a goal, deciding equalities by congruence closure instead of search, sharing work between overload candidates, and several engineering improvements;
  • soundness: nine problems of the existing implementation, each with a fix; four of them were found by independent testing against a reference resolver, by metamorphic testing and by adversarial review;
  • completeness: generic functions, extensions and conformances whose requirements or signatures mention an associated type of another requirement can now be used.

In the recommended configuration, the type checker is 4.5× faster on the standard library, and its output on the compiler's test suite is unchanged. On four patterns translated from the Swift and Rust standard libraries, the existing implementation takes 22 s on one and fails on the others (time limit, memory exhaustion, crash); all four are now checked in 16 to 700 ms.

Background

A given is a fact that resolution may use:
  • a conformance declaration, possibly generic and conditional, as in given <T where T is P> Box<T> is P;
  • a requirement of the enclosing declaration, such as T is P or A == B;
  • one of the built-in rules of equality: reflexivity, symmetry and transitivity.
Read as logic, a given of type <X̄> A₁, …, Aₙ ⟹ H is the definite Horn clause H ← A₁ ∧ … ∧ Aₙ, and resolution is SLD resolution over these clauses with three particularities.
  • Search order and selection. The search is breadth-first, and the first layer that contains a complete derivation determines the result. Within that layer, the derivation of minimal penalty is selected; givens from inner scopes have lower penalties. Several minimal derivations constitute an ambiguity error. The search is bounded at depth 10.
  • Premises as hypotheses. The premises of a conditional given become subgoals. They are discharged in last-in, first-out order, and while one is being discharged, those not yet discharged are available as hypotheses.
  • Coercions. When a given matches a goal up to some subterms, as P<A> and P<B> do, the equality A == B is assumed and becomes a subgoal, derived by the same procedure.
Three sources of cost follow from this design:
  • every visible given is tried at every step;
  • an underivable goal is rejected only after the search tree has been explored to the depth bound, at a cost exponential in the bound when givens branch;
  • derivations of equalities by symmetry and transitivity introduce fresh unification variables at each step, so the cost of an equality chain grows exponentially with its length, and the depth bound is soon exceeded.
Terminology.
  • A type is closed if it contains no unification variables.
  • An equality given is ground if it is closed and has neither generic parameters nor conditions of its own.
  • A technique is result-preserving if it does not change the set of minimal derivations, and hence neither the elaboration nor the diagnostics.
  • A fix is sound if every program it accepts has a derivation in the intended theory, and if it does not depend on the order of evaluation.

Performance techniques

The techniques in this section are result-preserving. Each is controlled by a runtime flag (shown in grey), which allows it to be measured and validated in isolation. Speed-ups quoted for a single technique are measured with only that technique enabled; they are not additive.

On the standard library, five techniques account for the entire gain. Adding them greedily, each time the one that helps most, gives 517 ms → 233 ms (index) → 177 ms (skipping extensions that do not declare the requested name) → 158 ms (typevec) → 138 ms (symindex) → 126 ms (traitindex); all techniques together give 130 ms. The remaining techniques matter only on the stress workloads, where each removes one super-polynomial behaviour, or are soundness fixes.

Candidate selection

Indexing givens by head constructor

index
Method
The givens visible from each scope are partitioned by the outermost type constructor of their conclusion. A goal with head P is matched only against the givens of partition P and against those whose conclusion has no fixed head. The original order and penalties are retained.
Correctness
In the absence of coercions, a given whose head differs from the goal's fails at its first unification. A failed alternative has no derivation and no descendants, so omitting it preserves the set of minimal derivations. The index is bypassed whenever a coercion could reconcile distinct heads: when an equality given, or a given with a variable head, is visible, or when an equality is assumed.
Effect
2.2× on the standard library; 81× with 40 unrelated conformances in scope.
Cost
One table per scope, built in time linear in the number of visible givens.

Caching non-sources of coercions

coesrc
Method
Before assuming an equality, the checker scans the visible givens for one that could derive it. A given whose conclusion is neither an equality nor a variable can derive no coercion. That classification is now recorded once per given, instead of being recomputed at each scan.
Correctness
The classification depends only on the given's declared type. It is recorded only once that type is final, that is, free of errors and not computed while a declaration is hidden from lookups.
Effect
1.2× on the standard library; 7.5× with many conformances in scope.
Cost
One set per module.

Refutation of underivable goals

Abstract least model

absmodel
Method
The least Herbrand model of the givens, read as Horn clauses, is infinite in general. The model is therefore computed in the finite domain of terms truncated at depth 2, following the depth-k abstraction of Sato and Tamaki[1]. Subterms below the bound are replaced by the wildcard ⊤, and so are types that are not first-order terms (functions, associated types).
  • Saturation is semi-naive and bottom-up.
  • Models are extended incrementally along the scope tree, and shared between files with identical imports.
  • A subgoal that unifies with no fact of the model is refuted before any alternative is formed for it.
Correctness
Over-approximation. The abstract model over-approximates every concrete derivation: truncation is monotone, ⊤ unifies with every term, and discarding premises can only add facts. A refuted goal therefore has no derivation, regardless of search order and depth bound, and refutation is result-preserving.
  • Hypotheses. Subgoals posed under hypotheses are covered by a cut argument: every hypothesis must itself be derived from the scope's givens before a derivation is accepted, so a subgoal that is underivable from the scope can only occur in derivations that fail.
  • Points the soundness argument depends on.
    • A repeated variable must not match a term containing ⊤, because two occurrences of ⊤ denote unrelated terms.
    • A cyclic binding is replaced by ⊤.
    • Facts are renamed apart from clauses.
    • File-level models are keyed by imports.
Effect
On div-branch, 1,471 ms in the existing implementation, 171 ms with the recommended techniques and 1.8 ms with the model; on div-loop-20, 115 ms, 7.6 ms and 3.2 ms. The cost of a refutable failure becomes independent of the depth bound: at bound 14, div-branch takes 44.5 s without the model and 3 ms with it.
Cost
About 1,400 facts for the standard library, computed in a few milliseconds. A fact deeper than the truncation bound weakens the model; it cannot make it unsound.

Abstract model in the presence of equalities

absquotient
Method
An equality given lets a derivation of P<A> serve, through a coercion, for P<B>. Since the model compares terms syntactically, it previously became inconclusive in any scope with an equality given. If all equality givens in scope are ground:
  1. their congruence closure is computed;
  2. every type constructor that occurs as the head of a member of a non-trivial class is declared opaque;
  3. every application of an opaque constructor is abstracted as ⊤, in clauses, facts and queries alike.
For A == B, only A and B become opaque. For Box<X> == Opt<Y>, every application of Box and of Opt does.
Correctness
Let X and Y be equal in the congruence closure. At the outermost position where they differ, both subterms belong to the same non-trivial class. Each is a member of it, or congruent to a member and therefore headed by the same constructor. Both are thus abstracted as ⊤ at that position, and their abstractions unify.
  • Generic givens. The abstraction depends only on the constructor at each position, so it commutes with substitution, and every instance of a generic given is covered.
  • Why per constructor. Opacity must be defined per constructor rather than per type. With Z == X and Box<X> == Opt<Y>, the type Box<Z> occurs in no equality but equals Opt<Y>. An abstraction per type would abstract it as Box(⊤), and could thereby refute a derivable goal.
Effect
The divergence-with-equality workload exhausts memory in the existing implementation, takes 2,205 ms with the fixes alone, the time needed to explore a divergent overload candidate up to the bound on derivations, and 4.3 ms with the model.
Cost
Models of such scopes are built afresh rather than extended. Equalities between compound types weaken the model.

Equality constraints

Decision procedure for closed equalities

eqsolve
Method
A goal A ~ B between closed types is decided without search:
  1. the ground equality facts in force are collected, from the hypotheses of the current derivation and from the scope;
  2. their congruence closure, together with the goal's terms, is computed with a signature table and union-find, in O(n log n)[2, 3, 4];
  3. the goal is refuted if A and B lie in distinct classes.
Otherwise a derivation is reconstructed from a minimal-cost path between them. The edges are weighted by the penalties the search would assign, so selection among alternative derivations is unchanged. This follows the lightest-derivation formulation of Knuth[5, 6].
Correctness
Equality of closed terms under finitely many ground equations is decidable, and congruence closure decides it. Neither the search nor the procedure uses injectivity of type constructors, so the procedure decides exactly the theory that the search explores, without its depth bound. The procedure defers to the search in every case it does not decide:
  • goals containing unification variables, an instance of rigid E-unification, which is NP-complete[7];
  • generic or conditional equality givens, under which the word problem is undecidable[8];
  • givens whose conclusion is a variable.
Associated types require two further rules, given under Soundness fixes.
Effect
With the other fixes: trans-8 from 1,211 ms to 1.3 ms, assoceq-8 from 3,286 ms to 7.9 ms, coercion-cache from 2,526 ms to 3.2 ms. The tuple-equalities workload terminates in 47 ms instead of exhausting memory. Ill-typed equality chains are rejected in milliseconds.
Cost
One small graph per closed equality goal.

Most general solutions of open equalities

eqmgu
Method
Because premises are discharged in reverse order, a requirement T == U is often discharged while U is still being inferred, which yields a goal A ~ ?u. For such a goal, where ?u does not occur in A, the single solution ?u := A is produced instead of a search over reflexivity, facts and transitivity.
Correctness
?u := A is the most general solution. Any other solution binds ?u to a type equal to A, and the remaining goals are invariant under the substitution of equals, because coercions transport derivations along derived equalities. The other solutions therefore add only redundant derivations, which previously manifested as spurious ambiguity errors.
  • The existing implementation could select another member of A's class, since a fact carries a lower penalty than reflexivity. The canonical choice made here is independent of the facts in scope.
Effect
Three-line programs that exhausted memory are checked in 0.2–0.3 s; ill-typed ones are rejected in 3 ms instead of 24 s.
Cost
One occurs check per open equality goal.

Keeping the index under equalities; deciding equalities at once

eqindex eqeager
Problem
One equality in scope, however unrelated to the goal, switched the index of givens off for every resolution in that scope. And each equality between corresponding parts of two types cost one search step, so that a given whose type differs from the goal in eight or more arguments could not be matched within the depth bound.
Method
The index remains valid when every equality in scope is ground and neither of its sides is a type constructor taking arguments: such equalities cannot relate two different head constructors. When a match leaves closed mismatching parts, the decision procedure is asked about each of them at once, in the environment in which the search would have asked; the resulting thread waits as many steps as the search would have spent, so that it completes at the same step and is ranked as before.
Correctness
Result-preserving, with one intended exception: a match that needs more equalities than the depth bound allows was rejected and is now accepted. The self-checking mode re-matches every skipped given and replays each resolution with the equalities proved by search.
Effect
With 40 conformances and one unrelated equality in scope, 4,480 candidate matches become 1,680.
Cost
About 200 lines. A resolution that fails at the depth bound can do more work before it fails, up to the work budget.

Set-based test for coercions

coeset stackscan
Problem
Before two mismatching types are assumed equal, a test asks whether any equality in scope could relate them. It compared the pair with every given in scope. While a where clause is being typed, the caches that absorb this cost are disabled, and typing n equalities between associated types was cubic: 2.2 s for 64 equalities. A helper used by the test also copied the whole program value at each call.
Method
A closed type can be related by a ground equality only if it is one of its sides. The sides of all ground equalities visible from a scope are collected once into a set, for the current state of the declarations being typed; the test for a closed pair is then two lookups.
Correctness
Result-preserving: the set contains exactly the types for which the per-given comparison succeeds. Givens that are not ground equalities take the existing path. The self-checking mode runs both tests and compares.
Effect
2.2 s → 0.09 s for 64 equalities; 405 ms → 43 ms on the signature of Swift's Collection translated to Hylo. Code without equalities is unaffected.
Cost
About 80 lines.

Member lookup

Skipping irrelevant extensions

memberskip
Method
A member lookup x.m tests, for each visible extension, whether it applies to the type of x; each test is a small resolution. An extension is now skipped when two conditions hold:
  • it declares no member named m;
  • its applicability test is known to have no side effect.
Correctness
The applicability test is not a pure function. It forces the computation of the extension's extended type, and possibly of the types of givens, and these results are memoized and read by later lookups. Omitting a test that would have computed something can change the order of these computations and thereby the result. The technique therefore skips a test only when everything it could compute is already memoized.
Effect
1.7× on the standard library and 15× on members-big, where the number of applicability tests falls from 4 million to 1,000. When extorder is enabled, this technique is redundant: extorder skips the same extensions unconditionally, at the price of changing the outcome of some cyclic programs. memberskip is the result-preserving alternative. With sigrounds the signature of every extension is known before the first lookup, the test has no side effect left to preserve, and every extension that does not declare the name is skipped: members-big takes 921 ms with memberskip alone and 380 ms in the recommended configuration.
Cost
A cache per extension.

Indexing traits by member name

traitindex
Method
A qualified lookup T.m considers only the visible traits that declare a member named m, in their original order.
Correctness
A trait without such a member contributes no candidate, and examining it has no side effect.
Effect
About 6% on the standard library; larger with many traits in scope.
Cost
One table per scope.

Overload resolution

Sharing work between candidates

twins cleanfirst lookahead
Problem
The constraint solver forks once per candidate of an overloaded name, and each fork solves everything that remains, so overloaded names nest. Three shapes are exponential:
  • a + a + … + a on Int: each + is both a member of Int and a requirement of a trait, two candidates of the same type; 14 operators cost 32,766 forks;
  • a wrong candidate is explored to the end, because nothing is cancelled before a first complete solution exists;
  • candidates that differ only in their result type are rejected by a goal examined after every overloaded name.
Method
  • twins Two candidates with the same type lead to the same search up to the declaration bound to the name, which the solver never reads. The second reuses the result of the first when both start from the same bound, or under any bound when the first search met no failure.
  • cleanfirst At the first overloaded name of a system, the solver first looks for a solution without diagnostics, with the bound "no error" from the start. If the first overloaded name has no clean candidate, the existing search runs unchanged.
  • lookahead During that search, a branch is abandoned when a goal still pending has closed types and is certain to fail.
Correctness
twins is result-preserving. The other two return the solution of the existing search, which is proved in the design and checked against an executable model on 1.2 million random constraint systems. They are nevertheless result-preserving for whole programs only together with the fix for declaration order (problem 5): they skip queries that the existing search makes in branches it later discards, and in the existing implementation such a query can decide which declaration is computed first. An adversarial review constructed five programs on which a verdict or a diagnostic changes for that reason.
Effect
Forks: 32,766 → 14 for 14 operators (with twins alone); 3,184 → 32 for eight calls with four overloads by parameter type; 349,524 → 36 for nine calls with four overloads by result type.
Cost
About 250 lines. Ill-typed statements run the existing search after a failed attempt, with up to twice the forks.

Soundness fixes

The changes in this section alter results by design. Each addresses a case in which the existing implementation accepts an ill-typed program, terminates abnormally, or yields a result that depends on the order of declarations. None alters the output on the test suite. Problems 1 to 5 were found while the optimizations were validated; problems 6 to 9 by independent testing and adversarial review.

1. Spurious equality derivations

fun g<T, U where T == U>() {}
fun f<V, W, D where V == W>() { g<D, V>() }   // accepted, although D == V does not follow

Cause. When a match succeeds only up to a coercion, the implementation assumes equalities between the mismatching subterms, but discards the bindings of unification variables made during the match. Subsequent steps may rebind those variables differently. The assumed equalities are then discharged for terms other than those compared, which yields a derivation of D == V from the unrelated fact V == W.

Fix fixsubst. The bindings are retained. Correct derivations of equalities are longer than the spurious ones, so this fix is viable only together with the decision procedure for equalities.

2. Exponential and depth-bounded equality derivations

fun f<T0, T1, T2, T3 where T0 == T1, T1 == T2, T2 == T3, T0 is P>(x: T3.X) { … }

Cause. A derivation of T0 == T3 by symmetry and transitivity requires about two steps per link, and the number of alternatives explored grows exponentially with the length of the chain. With more than four links, the depth bound is exceeded and valid programs are rejected.

Fix eqsolve, eqmgu. Closed equalities are decided by congruence closure, and open equalities of the form A ~ ?u are solved by their most general unifier.

3. Unreduced projections through pending requirements

extension <T where T is Collection, T.Element == Flag> Box<T> { fun first() -> Flag { … } }
fun g<T where T is Collection, T.Element == Flag>(b: Box<T>) { let f: Flag = b.first() }

Cause. The requirements of the extension are discharged in reverse order. When T.Element == Flag is discharged, its projection T.Element is qualified by the extension's own requirement T is Collection, which has not yet been discharged. No rule relates that projection to the caller's T.Element, so the equality is found only by an expensive search (1.4 s here), or not at all.

Fix eqsolve. The pending requirement is resolved in advance, in the environment in which it will later be discharged. The projection is identified with the corresponding projection of the caller only under two conditions: the resolution has a unique result, and every type involved is closed. Since resolution is deterministic, that result is the witness eventually used. Otherwise no refutation is drawn from the projection, and the search decides as before. Other forms of the problem remain open (see Limitations).

4. Cyclic bindings

given <U> => U is P<U> {}
given <T where T is P<S<T>>> => T is R {}
public fun main() { needR() }   // binds ?y := S<?y>; the compiler overflows its stack

Cause. Unification performs no occurs check. In addition, the variables of a function type's environment and those of method bundles were not reported by the predicate that tests whether a type contains unification variables.

Fix occurs, arrowenv. Cyclic bindings are rejected[9, 10]. The check covers every kind of type and runs in time linear in the size of the shared term. An occurs failure at the root of a match is treated as a mismatch; without this, it was treated as a successful match.

5. Dependence on the order of declarations

given A is P { type E = Int }
type X = A.E                       // needs `A is P`
given Box<X> is P { type E = A }   // needs `X`
// no cycle; accepted in 6 of the 24 orders of these declarations and one use of X

Cause. A lookup or a resolution computes the type of every candidate it meets, nested inside the computation that asked. A declaration whose type is being computed is hidden from lookups, to prevent infinite regress, and the answers computed without it are kept, errors included. Which declaration is hidden when it matters depends on which is computed first. Looking up A.E computes the types of all conformances in scope, including that of Box<X> is P, which needs the alias being defined. This is an instance of the general difficulty of scheduling name resolution soundly in type checkers[11]. Programs with genuine cycles are accepted or rejected depending on where evaluation enters the cycle.

Fix sigrounds. Extensions, conformances and givens with a written type are selected by lookups and resolutions through their type, their signature. All signatures of a module are computed before anything else, in rounds. A round starts from the untouched typing state and computes every signature; during the round, lookups and resolutions never compute a signature but read it from the table of the previous round, ignoring declarations without an entry. Rounds repeat until two consecutive tables are equal; if a table repeats without being stable, the declarations involved are reported. If the first round never ignored a declaration, it is final; this is the case for the standard library and the compiler's tests.

Order independence. The table after round k is a function of the program and of the table after round k − 1, so no table depends on the order of declarations. The argument needs four auxiliary rules, each found necessary by an adversarial review of the first implementation: only written signatures are in the table; the signature of an enclosing declaration is computed before a declaration nested in it; the signature of an extension or conformance is computed before a member selected through it; an alias of an erroneous type is an error. On the 129 programs constructed for this problem, type-checked in up to 24 orders of their declarations, no program has two verdicts (existing implementation: 52). Of 146 further programs written to design and to attack the fix, one has: a top-level given whose type is inferred from a global binding. Such givens are outside the table and are still typed on demand (see Limitations).

Cost. One round for code whose signatures do not depend on each other; two when a where clause selects a member through an earlier requirement. A chain of d dependent signatures takes d + 2 rounds, each recomputing every signature of the module.

6. Associated types of generic conformances

given <T> => T is P { type X = T; fun get() -> T { self }; fun put(x: T) {} }
fun q(a: A, c: C) { c.put(a.get()) }   // accepted: an A reaches code that expects a C

Cause. The associated type of a conformance was read from its declaration as written, without substituting the type arguments of the witness. Every instance of a generic conformance had the associated type T, equal to itself only. For a conditional conformance, the witnesses of its requirements were not substituted either.

Fix assocsubst. The type arguments and the requirement witnesses of the conformance are substituted into the definition. A conformance that defines nothing, as one required by a refined trait, selects the associated type through its own witness. Found by differential testing against a reference resolver.

7. Self.X equated with another witness's T.X

trait P { type X
  fun cast<T, U where T == Self, T is P, T.X == U>(x: U) -> X { conv<U, X>(x) } }
fun f<V, W where V == W, V is P, W is P>(v: V, x: W.X) { check<V.X>(v.cast<W, W.X>(x)) }   // accepted

Cause. The compiler's tests state that V.X and W.X differ when V == W and both conform through separate requirements: the two witnesses may define X differently. The unifier nevertheless treated Self.X, selected through the witness a trait stands for, as equal to a selection through any witness of an equal type, and the equality procedure followed it in a narrower form.

Fix abstractstrict. A selection through the witness that a trait declares is equal only to a selection through that witness at the same type. Two witness expressions are the same only if their types are syntactically equal: one requirement instantiated at two equal types is two witnesses. The cases in which the liberal rule did legitimate work (a given declared in a trait about its associated type; a member of an extension used at Self) are handled by substituting the actual witness.

8. A conformance satisfies the trait it refines with itself

trait Derived refines Base { fun g() }
given B is Derived { fun g() { self.f() } }   // accepted although nothing provides `B is Base`

Cause. A conformance is hidden while the traits it refines are checked. But the body of g had resolved B is Base earlier, with the conformance visible, and the memoized answer was returned without regard to what is hidden.

Fix hidecache. The memo of resolutions is not read while a given is deliberately hidden.

9. Members selected through an alias lose the type arguments

type AV = A<Void>
type AK = A<K>
fun use(a: AV, b: AK) { a.f(b.g()) }   // accepted: a K is passed where a Void is expected

Cause. The parameters of a generic type were replaced by the arguments of an instance only when the type of the receiver was written as an application. Through an alias the member kept the type's own parameter.

Fix aliasargs. Aliases are removed before the arguments are read, and the substitution reaches the aliased type of member aliases. Found by metamorphic testing.

Context independence of the equality procedure

A goal may be posed under different hypotheses, in different instantiations, and at different points of the evaluation order. A decision procedure must not depend on these circumstances. Three rules ensure this.

  • Selections through a declared witness (problem 7) are atoms: equal only to themselves. The theory is thus a fixed set of axioms per scope, and it is monotone: additional hypotheses never retract a conclusion.
  • Pending requirements (problem 3) are resolved in advance only in closed environments. A refutation that depends on an unresolved projection is not trusted. With the mechanism of the next section, a requirement that mentions another one is proved after it, and this special case is needed only for the heads of givens.
  • Hypotheses are used as facts only within the derivation that introduced them, and each must itself be derived before that derivation is accepted.

Resource bound

Some searches remain exponential: those that the abstract model cannot refute, because a fact exceeds the truncation depth and the givens branch. Previously they exhausted memory. With budget, a resolution whose frontier exceeds 100,000 alternatives is abandoned, and the checker reports an error. Reporting is essential: a silently failed resolution could otherwise steer overload or extension selection towards a different candidate.

Valid programs that were rejected

The changes in this section make the checker accept ordinary generic programs that the existing implementation rejects. With the fix for problem 6 they make the following program type-check; the existing implementation rejects each of its four calls.

trait Collection { type Element; fun first() -> Element }
trait Showable {}
given <T> => Bag<T> is Collection { type Element = T; … }
given Int8 is Showable {}
fun head<C where C is Collection>(c: C) -> C.Element { c.first() }
fun show<C where C is Collection, C.Element is Showable>(c: C) {}

fun use(b: Bag<Int8>) { let x: Int8 = head(b); show(b) }
fun generic<D where D is Collection, D.Element is Showable>(d: D) { let y: D.Element = head(d); show(d) }

Requirements that mention another requirement

premsubst premcommit
Problem
The type of show has two requirements, and the second mentions the associated type selected through the first. To call it, resolution assumes both and proves the last one first. At that moment nothing records that the selection refers to the first requirement of this very call, and that requirement has no witness yet; no given matches a type that mentions the callee's private declaration. Such a function, extension or conditional conformance could not be used by any caller.
Method
The type of an implication records the declaration through which later requirements refer to each requirement. When resolution opens it, a requirement that mentions an earlier one waits until that one is proved; the witness found is then substituted into its type, which is brought to the form name resolution gives (an associated type selected through a conformance declaration is replaced by its definition), and it is proved next. Every other requirement is treated as before.
Commitment
A requirement that another one mentions must be proved by the witness that resolving it alone gives. Otherwise the search would select, among all witnesses of A is Collection, one for which A.Element is Showable happens to hold, and a shadowed conformance could be chosen where name resolution at the call site chooses the nearest.
Correctness
Each requirement is proved once, and the witness substituted is the one in the derivation, so the elaborated call is well typed in the dependent reading of the clause. A resolution in which no requirement mentions another takes none of the new paths.
Cost
About 450 lines.

Associated types of a requirement in a signature

headsubst
Problem
The type of head mentions C.Element in its result. The constraint solver opens this type before the witness of C is Collection is known and checks arguments and result against a type that still names the callee's private declaration. No generic function whose signature mentions an associated type of its own requirement could be called.
Method
When the solver decomposes a call, each such associated type is replaced by a fresh type variable. When the callee has been elaborated, the variable is equated with the associated type selected through the witness passed for the requirement, reduced to its definition where there is one. The same substitution is applied to the members of an extension when the extension is found to apply, and to the head of a given, where a selection that faces a selection through a known witness decides the requirement.
Correctness
The equation is the dependent reading of the signature, with the witness of the elaborated call. Nothing is assumed about uniqueness of conformances: if a nearer conformance is in scope, it is passed, and its associated type is the one used.
Cost
About 330 lines.

Experiments that accept more programs

eqfilter eqouter eqclass heightbound
Equalities in matching
Matching uses an equality only between the innermost mismatching parts of two types, and only if both are written in an equality. Three flags let it use any closed pair the decision procedure proves, the outermost enclosing pair when the innermost is not derivable, and, for a part with unification variables, each type of its shape written in an equality. A generic conformance then applies to a type equal to an instance of its head (where T == Box<U>, given <X> => Box<X> is P). The pair is still proved by the existing mechanism, so nothing unsound is accepted, but more givens match: in constructed programs another conformance is selected, or a use becomes ambiguous.
Size of derivations
Resolution gives up after ten steps, counted over all the requirements of a call: a 5-tuple is not Copyable, and a function with ten requirements cannot be called. The fourth flag bounds the nesting of premises instead. Every derivation found today is still found.
Status
These depend on decisions that belong to the language designers and are not part of the recommended configuration.

Rejected approaches

The following approaches improve performance but are not result-preserving, and are therefore not adopted.

ApproachReason for rejection
Unconditionally skipping extensions that do not declare the requested nameApplicability tests have side effects on which later lookups depend (problem 5). Skipping them changed results on programs with interdependent extensions. The restricted form described above is result-preserving.
Pruning goals that repeat an ancestor (loop checking)The classical argument[12] assumes SLD resolution. Here, pending premises act as hypotheses, so a repeated goal can be cheaper than its ancestor. Pruning altered the selected derivations, lost derivations within the depth bound, and concealed ambiguities.
Deferring overloaded calls and branching on the most constrained firstThe order in which overloads are explored and ranked determines which solution is preferred and which ambiguities are reported. Altering it changed acceptance in both directions. The techniques under "Overload resolution" leave that order untouched.
Refuting equalities by equivalence classes without congruenceRejects valid programs that need a congruence step.

Superseded by sigrounds.
Rewriting types to canonical representatives of their equality classUnsafe here: conformances are selected by the way a type is written, so two types made identical by rewriting can have different associated types.

Limitations

Questions for the language designers

  • Coherence. The fixes assume, with the compiler's tests, that two conformances of equal types are distinct witnesses with distinct associated types. If conformances were coherent across equal types, problem 7 would be no problem, types could be normalized, and several restrictions here could be lifted.
  • Which witness a requirement gets. With premcommit, a requirement that another one mentions is proved by the witness that resolving it alone gives, and a tie is an ambiguity. The alternative solves the requirements together.
  • Ranking. Which of two derivations wins depends on the direction in which an equality is written and on the position of a requirement in a where clause, because penalties count pending requirements and derivations are ranked by the step at which they complete. Of 800 generated goals with two symmetric derivations, 408 are accepted and 392 reported as ambiguous.
  • Cycles between signatures. A program whose extensions and givens depend on each other is accepted when the rounds of problem 5 reach a stable table. A stricter rule could reject every such dependency.
  • Givens with an inferred type that a signature's resolution could see are rejected: their type must be written. Elsewhere they are typed on demand, and for a given declared outside a function the result can depend on the order of declarations, as in the existing implementation: let s = A() followed by given let g = s is accepted in 15 of the 24 orders of the test program. Requiring a written type for every given declared outside a function would close the case.
  • The bound on derivations counts steps, is not reported as such, and rejects valid programs; whether it is part of the language is undecided.

Known defects and gaps

  • Nested nominal types. A struct declared inside a generic conformance or a generic type is one type for all instances. This is unsound and outside the mechanisms studied here.
  • Recursion under a shadowing conformance. A recursive call made in a scope that declares a nearer conformance for the function's own requirement is rejected; the existing implementation accepts it with an inconsistent pair of witnesses.
  • Function values. A generic function whose signature mentions an associated type of its requirement can be called, but passing it as a value at a concrete type is still rejected.
  • Associated types through a refinement are opaque: T.X selected through T is R, where R refines P, is not identified with the definition in the conformance to P.
  • Aliases of generic types applied to arguments are not interchangeable with their expansion in the heads of givens and extensions.
  • Cost of dependent signatures. A chain of d signatures that depend on each other costs d + 2 rounds over the whole module.
  • Residual search. Equality goals containing unification variables inside types, such as Box<?v> ~ C, are still solved by search. Several inferred type arguments under equalities remain exponential, and the valid program is rejected by the resource bound at five.
  • Independent overloaded names that each have several clean candidates of different types remain exponential.

Validation

  • Output equivalence. A semantic dump records every inferred type, name binding with the site of its declaration, conformance table and diagnostic, together with the witness selected at each elaborated site. On the 192 tests and 24 workloads the dump of the result-preserving techniques is identical to that of the existing implementation. The dump is also identical with every fix enabled, in the recommended configuration and with all techniques: the test suite contains no program that exercises the defects.
  • Self-checking mode. With one flag, the checker re-does the work that each technique avoids and compares: every given skipped by the index is matched, every refutation is searched for, every equality decided at once is replayed by search, every round of signatures is recomputed in reverse order, every overload system is solved again by the existing search. This mode exposed defects that the corpus comparison did not show, among them an unsound refutation of equalities between method types and two order dependences of the computation of signatures.
  • Reference resolver. An independent specification of implicit resolution, written from the compiler's tests, and a resolver that follows it were compared with the checker on 21,500 generated queries. They exposed problem 6 and the incompleteness classes addressed under "Experiments"; on the 17,600 queries without associated types, a second independent model agrees with the reference, and the checker accepts none of the 8,192 invalid ones.
  • Metamorphic testing. 15,206 variants of 760 programs under eight meaning-preserving transformations (reordering declarations, requirements and type parameters; renaming; introducing aliases; adding tautologies) gave 370 verdict changes, attributed to declaration order (problem 5), aliases (problem 9), and the ranking and bound questions listed under Limitations. None is specific to the optimizations.
  • Declaration-order fuzzing. Each of 275 programs was type-checked in every order of its top-level declarations, up to 24 orders (6,092 runs), with the self-checking mode on. None of the 129 programs constructed for problem 5 has two verdicts (existing implementation: 52). Of the 146 programs of the design and of the attack on the fix, one has: a top-level given with an inferred type, which is outside the mechanism.
  • Adversarial review. Each design was reviewed, and each new mechanism attacked, by a reviewer whose task was to break it: about 550 programs, each with a control. The reviews found more than twenty defects in first implementations, six of them wrong acceptances; all are fixed and kept as regression tests. On the 1,651 programs of the compiler's tests, of the test programs and of these studies, the recommended configuration and the configuration with all techniques give the same verdicts, and the self-checking mode reports no violation.
  • Mutation. Of 716 ill-typed single-mutation variants of valid programs, the existing implementation accepts 29 and exhausts memory on 16; with the fixes all are rejected, the slowest in about 0.1 s.

Threats to validity

  • The correctness arguments are informal; none is mechanized. For the mechanisms of problems 5 to 9 and of dependent requirements, the adversarial reviews found errors in arguments that had seemed complete, and nothing guarantees that they found the last.
  • Hylo has no large body of generic code. The standard library has no equality constraint and no associated type in a signature, so the mechanisms that concern them are exercised only by programs written for this work and by four translated library patterns.
  • The reference specification contains guesses where the compiler's tests are silent, and the expected verdicts of the attack programs were established by reasoning, not by an authority on the language.
  • Most stress workloads are synthetic. They show how a behaviour scales, not how often it occurs.
  • Timings come from a single virtual machine; repeated sessions differ by up to 20%. Work counters, which are deterministic, are the primary measure throughout.

Using the implementation

The implementation is a series of 31 patches to the Hylo front end (patches/ in the accompanying archive), about 4,100 added lines. Each technique is enabled through the environment variable HYLO_TC_EXPERIMENTS:

Result-preserving, for the existing implementation: index,typevec,symindex,traitindex,memberskip,twins,stackscan,coeset
Fixes: occurs,fixsubst,eqsolve,eqmgu,arrowenv,budget,sigrounds,assocsubst,abstractstrict,hidecache,aliasargs,premsubst,premcommit,headsubst,dedup
Recommended: both lists, together with eqindex,eqeager,cleanfirst,lookahead,reifymemo
Experiments: eqfilter,eqouter,eqclass,heightbound; validation: selfcheck, trace

The fixes depend on each other: fixsubst requires occurs and eqsolve; premcommit and dedup belong with premsubst; headsubst requires assocsubst and abstractstrict; cleanfirst and lookahead require sigrounds. With sigrounds, the earlier order checks (extorder, givencheck) and memberskip are inactive.

Related work

Resolution as logic programming. Viewed as Horn clauses, givens make resolution a form of proof search. For propositional clauses, derivability is decidable in linear time[13, 14]; with variables, it is undecidable in general. The abstract model adopts the depth-k abstraction of Sato and Tamaki[1], one of several finite approximations of the success set of a logic program[15, 16, 17, 18, 19]. Non-failure analysis[20] is the closest precedent for using such approximations to establish that a call cannot succeed. The rejected loop check derives from the analysis of loop-checking mechanisms by Bol, Apt and Klop[12], whose soundness results presuppose plain SLD resolution.
Minimal derivations. Selecting the derivation of least cost, and reporting ties, is an instance of Knuth's generalization of shortest paths to grammars[5], subsequently formulated as weighted deduction[6, 21]. The counting of ties corresponds to semiring parsing[22].
Type-class resolution in other languages.
  • Repeated and cyclic subgoals: Lean 4 handles them by tabling[23], and the next-generation Rust trait solver by canonical-goal caching and fixed-point iteration[24].
  • Divergence: Scala 3 and GHC address it with termination conditions[25, 26]; the resource bound adopted here is a weaker alternative.
  • Coherence: the requirement that equally ranked derivations denote equivalent programs has been studied by Bottu et al.[27] and in the COCHIS calculus[28]. Quantified constraints[29] explain why generic equality givens defeat first-order models.
  • Type equivalence: Swift decides it by Knuth–Bendix completion of a rewriting system[30], an alternative to the congruence closure used here.
Equational reasoning. The equality procedure rests on congruence closure[2, 3] and union-find[4]. Its scope reflects known complexity results: rigid E-unification is NP-complete[7], and the word problem for general equational theories is undecidable[8]. The occurs check is part of syntactic unification from its inception[9, 10].
Indexing. Partitioning givens by head constructor is the first level of discrimination-tree and substitution-tree indexing[31, 32], as used for instance selection in Lean[33] and GHC[26].
Overload resolution. Overload resolution is NP-complete in general[34]. Polynomial algorithms exist for restricted settings such as Ada[35], and techniques from constraint satisfaction[36] prune the search in practice. Swift's solver combines a constraint graph with the pruning of disjunctions[37]. Bidirectional type checking[38] offers a complementary means of reducing the number of candidates by propagating expected types.
Name resolution and scheduling. Problem 5 is an instance of answering a name-resolution query before all information that bears on it is available. Scope graphs provide a formal account of name resolution[39, 40], and subsequent work gives criteria under which a query may be answered soundly[11, 41]. It also shows how resolution queries can be specialized for performance[42] and scaled to large code bases[43]. The memoization arguments for memberskip and coesrc follow the build-system view of incremental computation[44, 45].
