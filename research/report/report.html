Hylo Type-Checker Optimizations

Hylo's type checker spends most of its time on implicit resolution: finding the given (conformance, where-clause requirement or equality) that proves a goal like T is P. This report describes a set of techniques that make it 4× faster on the standard library and 10–1000× faster on hard cases. It also covers the soundness bugs of the existing checker found along the way, and how each one is fixed.

Background: how implicit resolution works

A given is something the checker may use as a proof:

  • a conformance declaration (given Int is P), possibly generic and conditional (given <T where T is P> Box<T> is P);
  • a where-clause requirement of the enclosing function (T is P, A == B);
  • one of three built-in equality rules: reflexivity, symmetry and transitivity.

To prove a goal, the checker matches it against every visible given. A conditional given turns its conditions into new goals. The search is breadth-first, so the first layer of the search tree that contains a complete proof wins. Within that layer, the proof with the lowest penalty is chosen, where givens from inner scopes are cheaper. A tie is reported as ambiguity. The search gives up after 10 steps.

Equalities enter through coercions. When a given almost matches a goal (P<A> against P<B>), the checker may assume A == B and must then prove that equality as another goal, using the same search.

Three things follow from this design:

  • Many givens in scope means many dead branches at every step.
  • A goal that cannot be proved is only rejected after the whole tree up to the depth cap has been explored, which is exponential in the cap.
  • Equality reasoning by symmetry and transitivity creates new open goals at each step, so equality chains are exponential in their length and soon exceed the cap.

Speed-ups

Each technique below changes only how much work the checker does, never the result. Every one is a runtime flag (in grey), so it can be measured and verified on its own.

Try only the givens that can match

Index givens by their head

index
Idea
Group the givens of each scope by the outermost type constructor of what they prove. A goal P<…> only tries the givens that prove P<…>, plus the few that could prove anything. Order and penalties are kept.
Correct because
A given with a different head fails at its first step and has no effect on the search. The index is not used where a coercion could make two different heads match: when an equality given is visible, or when an equality is assumed.
Effect
2.2× on the standard library, 81× with 40 unrelated conformances in scope.
Cost
One small table per scope.

Remember givens that can never produce a coercion

coesrc
Idea
Before assuming an equality, the checker scans all givens for one that could prove it. A given whose type is not an equality, and not a fully generic <T> T, can never help. It is now classified once instead of on every scan.
Correct because
The classification depends only on the given's own type.
Effect
1.2× on the standard library, 7.5× with many conformances in scope.
Cost
One set per module.

Prove early that a search will fail

Abstract model of the givens

absmodel
Idea
This answers the question that started the project: a cheap, sound test that resolution will fail.
  • Read each given as a logic rule: given <T where T is P> Box<T> is Q becomes "Q(Box(T)) if P(T)".
  • Compute everything the rules can derive, with types cut off below depth 2 (deeper parts become a wildcard), so the computation is finite.
  • A goal that matches nothing in that set cannot be proved, and is rejected at once.
Correct because
The cut-off set contains a match for every provable goal, because cutting off and wildcards only add matches. A rejected goal therefore had no proof, and no result, penalty or ambiguity changes. Goals proved under temporary assumptions are covered too: those assumptions must themselves be proved from the scope before a proof is accepted.
Effect
Failing and looping searches no longer explore the tree to the depth cap: 734× on div-branch, 51× on div-loop-20. The cost of a refutable failure no longer grows with the cap.
Cost
About 1,400 derived facts for the standard library, a few ms. Facts deeper than the cut-off make the model weaker, never wrong.

Keep the model working when equalities are in scope

absquotient
Idea
An equality requirement like where A == B lets a proof of P<A> stand for P<B>, which the model above cannot see, so it used to switch itself off. Instead, every type constructor that appears in a non-trivial equality is treated as a wildcard. For A == B that is just A and B; for Box<X> == Opt<Y> it is every Box and every Opt.
Correct because
Two types that are equal under the equalities first differ at a position whose constructor takes part in an equality. Both sides become wildcards there, so they still match.
  • The wildcard is chosen per constructor, not per type. A type that never appears in the equalities can still equal one that does (Box<Z> when Z == X and Box<X> == Opt<Y>), and so can the instance of a generic given. Erasing whole constructors covers both.
  • The erasure depends only on the constructor at each position, so it commutes with substituting the parameters of generic givens.
Effect
The "divergence + equality" program goes from out of memory to 3 ms.
Cost
The model of such a scope is rebuilt rather than inherited from the enclosing scope. Equalities between compound types weaken it.

Decide equalities instead of searching for them

Equality decision procedure

eqsolve
Idea
When a goal is an equality between types with no unknowns, the checker no longer searches:
  • It collects the equality facts that hold in that place.
  • It computes their congruence closure: which types are equal, including Box<A> == Box<B> when A == B.
  • It answers yes or no directly, in O(n log n).
A "yes" comes with a proof built from the cheapest chain of facts. That chain carries the same penalty the search would have given it, so the choice between alternative proofs does not change.
Correct because
Equality between closed types under closed equations is decidable, and congruence closure decides it exactly for the rules the search uses. The procedure steps back and lets the search run in every case it cannot decide:
  • the goal has unknowns (rigid E-unification);
  • an equality is generic or conditional (the word problem, which is undecidable);
  • a given could prove anything.
Two refinements are needed for associated types; they are explained under Correctness fixes.
Effect
trans-8 306×, assoceq-8 37×, coercion-cache 552×. The 31-equality tuple program goes from out of memory to 63 ms. Ill-typed equality chains are rejected in milliseconds instead of being wrongly accepted after seconds.
Cost
A small graph is built per equality goal.

Solve "find a type equal to X" directly

eqmgu
Idea
A requirement like where T == U is often checked while U is still being inferred, which gives the goal A ~ ?u. The search used to try reflexivity, every fact and every transitivity step, each creating new open goals. Now the checker simply sets ?u := A.
Correct because
This is the most general answer: any other answer is a type equal to A, and the remaining goals hold for one exactly when they hold for the other. The extra answers used to show up only as false ambiguity errors.
Effect
Programs of three lines that ran out of memory now take 0.2–0.3 s. Ill-typed ones are rejected in 3 ms instead of 24 s.
Cost
None measurable. The checker now always picks A itself, where the old search sometimes picked another type known to be equal to it.

Faster member lookup

Skip extensions that cannot matter

memberskip
Idea
Looking up x.m used to check, for every visible extension, whether it applies to x's type. Each check is a small resolution. Now an extension is skipped when it declares no member named m, and when checking it is known to have no side effect.
Correct because
The applicability check can force the computation of types that other lookups then reuse, so skipping it could change the order of those computations and, with it, results. The skip is restricted to cases where everything the check could compute is already computed.
Effect
1.7× on the standard library and 15× on members-big. The applicability checks on members-big drop from 4 million to 1000.
Cost
A small cache per extension.

Index traits by member name

traitindex
Idea
A lookup like T.m visits only the traits that declare m, instead of every visible trait.
Correct because
A trait without m contributes nothing, and the order of the rest is kept.
Effect
Small (about 6% on the standard library); it matters with many traits.
Cost
One table per scope.

Correctness fixes

These change results on purpose. Each one fixes a way in which the existing checker accepts an ill-typed program, crashes, or gives an answer that depends on declaration order. None of them changes any result in the compiler's test suite.

1. Unrelated equalities make types interchangeable

fun g<T, U where T == U>() {}
fun f<V, W, D where V == W>() { g<D, V>() }   // accepted, although nothing says D == V

Cause. When the checker assumes an equality to make a given fit, it forgets the type-variable bindings it made while matching. A later step can then bind the same variable differently, so the fact V == W ends up "proving" D == V.

Fix fixsubst. The bindings are kept. Honest equality proofs then need more steps, so this fix only works together with the decision procedure (eqsolve), which needs none.

2. Equality chains time out or are rejected

fun f<T0, T1, T2, T3 where T0 == T1, T1 == T2, T2 == T3, T0 is P>(x: T3.X) { … }

Cause. Proving T0 == T3 by searching through symmetry and transitivity is exponential in the length of the chain, and it needs about two steps per link. Beyond four links the 10-step cap is exceeded and valid programs are rejected.

Fix eqsolve, eqmgu. A decision procedure takes the place of the search (see Speed-ups).

3. Associated types through a callee's requirements are not simplified

extension <T where T is Collection, T.Element == Flag> Box<T> { fun first() -> Flag { … } }
fun g<T where T is Collection, T.Element == Flag>(b: Box<T>) { let f: Flag = b.first() }

Cause. The checker verifies the extension's requirements one by one, in reverse order. When it checks T.Element == Flag, the T.Element in that requirement still refers to the extension's own, not-yet-proved T is Collection. Nothing connects it to the caller's T.Element, so the equality can only be found by a slow search (1.4 s here), or not at all.

Fix eqsolve. The pending requirement T is Collection is resolved first. If that resolution has a single answer, and nothing it depends on is still unknown, T.Element is identified with the caller's (17 ms). Otherwise no verdict is drawn from it, and the search decides as before. This covers the common case; other forms of the problem remain (see Limitations).

4. A type variable bound to a type containing itself crashes the compiler

given <U> => U is P<U> {}
given <T where T is P<S<T>>> => T is R {}
public fun main() { needR() }   // the checker binds ?y := S<?y> and overflows its stack

Cause. Unification has no occurs check. The same defect also hid in a few kinds of type: the variables of a closure's environment were invisible, and so were those of method bundles.

Fix occurs, arrowenv. Cyclic bindings are refused. The check covers every kind of type, takes linear time on shared terms, and treats a failure at the top of a match as a mismatch (before the fix, such a failure was treated as a match, so a Void value could stand in for a proof).

5. Results depend on declaration order

given T is P { type Y = U }
given U is Q { type O = T }
given Z.O is P { type Y = Int }   // accepted…
type Z = T.Y                      // …but rejected when these two lines are swapped

Cause. While the checker computes the type of a declaration, it hides that declaration from lookups, and it remembers the answers of those lookups. Here, computing the type of given Z.O is P needs T.Y, which needs T is P, and the given being computed is hidden. Whether the hidden declaration would have changed the answer is never checked, so the outcome depends on which declaration happens to be computed first. Extensions whose extended type depends on other extensions have the same problem.

Fix givencheck, extorder. Every lookup that skipped a hidden declaration is recorded. Once all the declarations involved are known, the checker tests whether the hidden one could have taken part. If it could, the program is reported as circular, in every order. If it could not, the skip was harmless, and the program is accepted as before.

Making the equality procedure safe in every context

The same goal can be posed in different contexts: under different temporary assumptions, in different generic instantiations, at different points of the order of computation. A decision procedure must give an answer that does not depend on such accidents. Three rules ensure that:

  • Associated types of Self. Inside a trait, Self.X is the trait's own, abstract associated type. The language says it equals T.X when T == Self, and the old search used that rule (accepted test v-abs-7). The language also says that T.X and U.X differ when they come from two different conformances, even if T == U (negative test associated-type-inequality). Applying the first rule freely contradicts the second: with T == Self and U == Self, it gives T.X == Self.X == U.X. The procedure therefore equates Self.X with T.X only when the scope has exactly one conformance to the trait for a type equal to Self. That is decided from the scope's own declarations, never from the goal or from temporary assumptions, so it is the same everywhere, and assuming more never takes a conclusion back.
  • Pending requirements (fix 3) are resolved ahead of time only when nothing they depend on is still unknown. A "no" answer that depends on an unresolved one is not trusted: the search decides instead.
  • Temporary assumptions are used as facts only for the duration of the proof that made them. Every one of them must itself be proved before a result is accepted.

Bounding runaway searches

Some searches still grow exponentially: goals the abstract model cannot refute, with branching givens. The old checker ran out of memory on them. With budget, a search whose frontier passes 100,000 candidates is abandoned and reported as "implicit resolution is too complex". The report is an error, so an abandoned search can never silently make the checker pick a different overload or extension.

Approaches that do not work

These looked promising and are faster. They are not used because each one changes results.

IdeaWhy it fails
Skip extensions without the looked-up name, unconditionallyChecking an extension has side effects that later lookups depend on (see fix 5). Skipping it changed results on programs with interdependent extensions. The restricted version above is safe.
Prune a goal that repeats one of its ancestors (loop check)The classic argument assumes plain logic-programming search. Hylo lets pending requirements act as assumptions, so a repeated goal can be cheaper than its ancestor. Pruning changed chosen proofs, lost valid proofs and hid ambiguities.
Delay overload choices and try the most constrained firstThe order in which the checker ranks overloads is part of the meaning of a program. Changing it flipped acceptance in both directions.
Refute equalities by grouping types into classes, without congruenceIt rejected a valid program, because associated types of Self can be equal through their trait (see above).
Undo every result computed during a cyclic lookupIt accepted an ambiguous program, its verdict still depended on order, and undoing was expensive.
Cache coercion checks made under assumptionsSafe, but no faster: those checks were already cheap.

Limitations

  • Return-type overloads stay exponential. g(h(), h(), …) with h overloaded on its return type takes 8 s for 9 arguments. Fixing this needs an overload solver that prunes candidates without changing the order in which the checker ranks them.
  • Mutually recursive extensions are rejected. Two extensions whose extended types depend on each other's members are reported as circular, even when only one reading is consistent: 
    extension A.Inner.Foo { type Inner = Bool }   // needs Foo, provided by the next extension
extension A.Inner { type Foo = Int }          // needs Inner in A, which the first one might provide
    The old checker accepted this only by accident of evaluation order. Accepting it in every order would need a fixed-point computation.
  • The complexity limit can reject valid programs. With the fixes but without the speed-ups, a few valid programs with looping givens reach it; with the abstract model they do not.
  • Some equalities still need the search:
    • goals with unknowns inside a type (Box<?v> ~ C);
    • associated types reached through more complex forms of pending requirements.

Validation

  • Identical results on the test suite. A semantic dump compares every expression type, name binding, implicit argument, conformance table and diagnostic with the existing checker. It is identical on the compiler's 192 tests and 24 workloads, with the fixes alone and with everything enabled.
  • Adversarial programs. 520 small programs written specifically to break each technique cover unsound acceptance, crashes, order dependence and slow cases. Each claimed problem was confirmed by re-running it, and every confirmed one is fixed. On these programs, the existing checker crashes 21 times and times out (30 s) 43 times. The new one never crashes and times out once, on a return-type overload. Every changed verdict is one of these:
    • an ill-typed program that is now rejected;
    • a crash or timeout that now gets an answer;
    • the mutually-recursive-extension case above.
  • An argument per technique. Each technique comes with the reason it cannot change a result, given above and in full in the per-technique documents.

Using the patches

The work is a series of 12 patches on the Hylo front end (patches/ in the archive). Every technique is a switch, set with HYLO_TC_EXPERIMENTS:

Fixes only: occurs,fixsubst,eqsolve,extorder,arrowenv,eqmgu,givencheck,budget
All (recommended): the fixes plus symindex,coesrc,traitindex,memberskip,unify,index,absmodel,absquotient,typevec,reifymemo

The fixes should land together: fixsubst needs occurs (without it, new crashes appear) and eqsolve (without it, equality chains hit the depth cap).

Related work

Resolution as logic programming. Givens are Horn clauses, and resolution is proof search. For clauses without variables, provability takes linear time[1, 2]; with variables, it is undecidable in general. The abstract model uses depth-k abstraction[3], one of several finite approximations of what a logic program can derive[4, 5, 6, 7, 8]. Non-failure analysis[9] is the closest earlier use of such approximations to show that a call must fail. The rejected loop check comes from the loop-checking literature[10], whose soundness argument assumes plain SLD resolution.
Smallest proofs. Choosing the cheapest proof and reporting ties is Knuth's generalization of shortest paths[11], also known as weighted deduction[12, 13]; counting ties is semiring parsing[14]. The equality procedure rebuilds its proofs as cheapest paths for this reason.
Type classes and traits elsewhere.
  • Repeated and cyclic subgoals: Lean 4 tables them[15], and Rust's new trait solver caches canonical goals and computes fixed points[16].
  • Divergence: Scala 3 and GHC bound it with termination checks[17, 18]; the complexity limit here is a cruder relative.
  • Coherence: the requirement that equally good proofs mean the same program is studied by Bottu et al.[19] and in COCHIS[20]. Quantified constraints[21] explain why generic equalities defeat the simple models.
  • Equality of types: Swift decides it with a rewrite system completed by Knuth–Bendix[22].
Equality. The equality procedure is congruence closure[23, 24] over union-find[25]. Its limits follow the decidability results: equations with unknowns are rigid E-unification, which is NP-complete[26], and general equations raise the word problem, which is undecidable[27]. The occurs check belongs to unification from its origin[28, 29].
Indexing. Grouping givens by head constructor is the first level of discrimination-tree and substitution-tree indexing[30, 31], as in Lean's instance index[32] and GHC's rough-match keys[18].
Overloading. Overload resolution is NP-complete in general[33]. Ada has polynomial cases[34], and constraint-satisfaction pruning helps in practice[35]. Swift's solver combines a constraint graph with pruning of overload choices[36].
Name resolution and evaluation order. Fix 5 is an instance of a known problem: a type checker answers a name query before everything that could affect the answer is known. Scope graphs formalize name resolution[37], and later work gives criteria for when a query may safely be answered[38, 39]. Skipping only work whose inputs are settled follows the build-system view of incremental computation[40, 41].
