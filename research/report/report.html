Hylo Type-Checker Optimizations

Implicit resolution, the search for a derivation of a constraint such as T is P from the givens in scope, dominates the running time of Hylo's type checker. This report presents techniques that reduce its cost and the soundness problems of the existing implementation they expose.

The techniques fall into four groups:

  • restricting the candidate givens to those that can match a goal;
  • refuting goals by an abstract least model of the givens;
  • deciding equalities between closed types by congruence closure;
  • several engineering improvements.

The report also identifies five soundness problems of the existing implementation and gives a fix for each; the fix for dependence on declaration order is partial. With all techniques enabled, the type checker is 4.1× faster on the standard library, and up to three orders of magnitude faster on workloads designed to stress resolution. Its output is unchanged on the compiler's test suite.

Background

A given is a fact that resolution may use:
  • a conformance declaration, possibly generic and conditional, as in given <T where T is P> Box<T> is P;
  • a requirement of the enclosing declaration, such as T is P or A == B;
  • one of the built-in rules of equality: reflexivity, symmetry and transitivity.
Read as logic, a given of type <X̄> A₁, …, Aₙ ⟹ H is the definite Horn clause H ← A₁ ∧ … ∧ Aₙ, and resolution is SLD resolution over these clauses with three particularities.
  • Search order and selection. The search is breadth-first, and the first layer that contains a complete derivation determines the result. Within that layer, the derivation of minimal penalty is selected; givens from inner scopes have lower penalties. Several minimal derivations constitute an ambiguity error. The search is bounded at depth 10.
  • Premises as hypotheses. The premises of a conditional given become subgoals. They are discharged in last-in, first-out order, and while one is being discharged, those not yet discharged are available as hypotheses.
  • Coercions. When a given matches a goal up to some subterms, as P<A> and P<B> do, the equality A == B is assumed and becomes a subgoal, derived by the same procedure.
Three sources of cost follow from this design:
  • every visible given is tried at every step;
  • an underivable goal is rejected only after the search tree has been explored to the depth bound, at a cost exponential in the bound when givens branch;
  • derivations of equalities by symmetry and transitivity introduce fresh unification variables at each step, so the cost of an equality chain grows exponentially with its length, and the depth bound is soon exceeded.
Terminology.
  • A type is closed if it contains no unification variables.
  • An equality given is ground if it is closed and has neither generic parameters nor conditions of its own.
  • A technique is result-preserving if it does not change the set of minimal derivations, and hence neither the elaboration nor the diagnostics.
  • A fix is sound if every program it accepts has a derivation in the intended theory, and if it does not depend on the order of evaluation.

Performance techniques

The techniques in this section are result-preserving. Each is controlled by a runtime flag (shown in grey), which allows it to be measured and validated in isolation. Speed-ups quoted for a single technique are measured with only that technique enabled; they are not additive.

On the standard library, five techniques account for the entire gain. Adding them greedily, each time the one that helps most, gives 517 ms → 233 ms (index) → 177 ms (skipping extensions that do not declare the requested name) → 158 ms (typevec) → 138 ms (symindex) → 126 ms (traitindex); all techniques together give 130 ms. The remaining techniques matter only on the stress workloads, where each removes one super-polynomial behaviour, or are soundness fixes.

Candidate selection

Indexing givens by head constructor

index
Method
The givens visible from each scope are partitioned by the outermost type constructor of their conclusion. A goal with head P is matched only against the givens of partition P and against those whose conclusion has no fixed head. The original order and penalties are retained.
Correctness
In the absence of coercions, a given whose head differs from the goal's fails at its first unification. A failed alternative has no derivation and no descendants, so omitting it preserves the set of minimal derivations. The index is bypassed whenever a coercion could reconcile distinct heads: when an equality given, or a given with a variable head, is visible, or when an equality is assumed.
Effect
2.2× on the standard library; 81× with 40 unrelated conformances in scope.
Cost
One table per scope, built in time linear in the number of visible givens.

Caching non-sources of coercions

coesrc
Method
Before assuming an equality, the checker scans the visible givens for one that could derive it. A given whose conclusion is neither an equality nor a variable can derive no coercion. That classification is now recorded once per given, instead of being recomputed at each scan.
Correctness
The classification depends only on the given's declared type. It is recorded only once that type is final, that is, free of errors and not computed while a declaration is hidden from lookups.
Effect
1.2× on the standard library; 7.5× with many conformances in scope.
Cost
One set per module.

Refutation of underivable goals

Abstract least model

absmodel
Method
The least Herbrand model of the givens, read as Horn clauses, is infinite in general. The model is therefore computed in the finite domain of terms truncated at depth 2, following the depth-k abstraction of Sato and Tamaki[1]. Subterms below the bound are replaced by the wildcard ⊤, and so are types that are not first-order terms (functions, associated types).
  • Saturation is semi-naive and bottom-up.
  • Models are extended incrementally along the scope tree, and shared between files with identical imports.
  • A subgoal that unifies with no fact of the model is refuted before any alternative is formed for it.
Correctness
Over-approximation. The abstract model over-approximates every concrete derivation: truncation is monotone, ⊤ unifies with every term, and discarding premises can only add facts. A refuted goal therefore has no derivation, regardless of search order and depth bound, and refutation is result-preserving.
  • Hypotheses. Subgoals posed under hypotheses are covered by a cut argument: every hypothesis must itself be derived from the scope's givens before a derivation is accepted, so a subgoal that is underivable from the scope can only occur in derivations that fail.
  • Points the soundness argument depends on.
    • A repeated variable must not match a term containing ⊤, because two occurrences of ⊤ denote unrelated terms.
    • A cyclic binding is replaced by ⊤.
    • Facts are renamed apart from clauses.
    • File-level models are keyed by imports.
Effect
734× on div-branch and 51× on div-loop-20. The cost of a refutable failure becomes independent of the depth bound: at bound 14, div-branch takes 44.5 s without the model and 3 ms with it.
Cost
About 1,400 facts for the standard library, computed in a few milliseconds. A fact deeper than the truncation bound weakens the model; it cannot make it unsound.

Abstract model in the presence of equalities

absquotient
Method
An equality given lets a derivation of P<A> serve, through a coercion, for P<B>. Since the model compares terms syntactically, it previously became inconclusive in any scope with an equality given. If all equality givens in scope are ground:
  1. their congruence closure is computed;
  2. every type constructor that occurs as the head of a member of a non-trivial class is declared opaque;
  3. every application of an opaque constructor is abstracted as ⊤, in clauses, facts and queries alike.
For A == B, only A and B become opaque. For Box<X> == Opt<Y>, every application of Box and of Opt does.
Correctness
Let X and Y be equal in the congruence closure. At the outermost position where they differ, both subterms belong to the same non-trivial class. Each is a member of it, or congruent to a member and therefore headed by the same constructor. Both are thus abstracted as ⊤ at that position, and their abstractions unify.
  • Generic givens. The abstraction depends only on the constructor at each position, so it commutes with substitution, and every instance of a generic given is covered.
  • Why per constructor. Opacity must be defined per constructor rather than per type. With Z == X and Box<X> == Opt<Y>, the type Box<Z> occurs in no equality but equals Opt<Y>. An abstraction per type would abstract it as Box(⊤), and could thereby refute a derivable goal.
Effect
The divergence-with-equality workload no longer exhausts memory and is checked in 3.1 ms.
Cost
Models of such scopes are built afresh rather than extended. Equalities between compound types weaken the model.

Equality constraints

Decision procedure for closed equalities

eqsolve
Method
A goal A ~ B between closed types is decided without search:
  1. the ground equality facts in force are collected, from the hypotheses of the current derivation and from the scope;
  2. their congruence closure, together with the goal's terms, is computed with a signature table and union-find, in O(n log n)[2, 3, 4];
  3. the goal is refuted if A and B lie in distinct classes.
Otherwise a derivation is reconstructed from a minimal-cost path between them. The edges are weighted by the penalties the search would assign, so selection among alternative derivations is unchanged. This follows the lightest-derivation formulation of Knuth[5, 6].
Correctness
Equality of closed terms under finitely many ground equations is decidable, and congruence closure decides it. Neither the search nor the procedure uses injectivity of type constructors, so the procedure decides exactly the theory that the search explores, without its depth bound. The procedure defers to the search in every case it does not decide:
  • goals containing unification variables, an instance of rigid E-unification, which is NP-complete[7];
  • generic or conditional equality givens, under which the word problem is undecidable[8];
  • givens whose conclusion is a variable.
Associated types require two further rules, given under Soundness fixes.
Effect
306× on trans-8, 37× on assoceq-8 and 552× on coercion-cache. The tuple-equalities workload terminates in 63 ms instead of exhausting memory. Ill-typed equality chains are rejected in milliseconds.
Cost
One small graph per closed equality goal.

Most general solutions of open equalities

eqmgu
Method
Because premises are discharged in reverse order, a requirement T == U is often discharged while U is still being inferred, which yields a goal A ~ ?u. For such a goal, where ?u does not occur in A, the single solution ?u := A is produced instead of a search over reflexivity, facts and transitivity.
Correctness
?u := A is the most general solution. Any other solution binds ?u to a type equal to A, and the remaining goals are invariant under the substitution of equals, because coercions transport derivations along derived equalities. The other solutions therefore add only redundant derivations, which previously manifested as spurious ambiguity errors.
  • The existing implementation could select another member of A's class, since a fact carries a lower penalty than reflexivity. The canonical choice made here is independent of the facts in scope.
Effect
Three-line programs that exhausted memory are checked in 0.2–0.3 s; ill-typed ones are rejected in 3 ms instead of 24 s.
Cost
One occurs check per open equality goal.

Member lookup

Skipping irrelevant extensions

memberskip
Method
A member lookup x.m tests, for each visible extension, whether it applies to the type of x; each test is a small resolution. An extension is now skipped when two conditions hold:
  • it declares no member named m;
  • its applicability test is known to have no side effect.
Correctness
The applicability test is not a pure function. It forces the computation of the extension's extended type, and possibly of the types of givens, and these results are memoized and read by later lookups. Omitting a test that would have computed something can change the order of these computations and thereby the result. The technique therefore skips a test only when everything it could compute is already memoized.
Effect
1.7× on the standard library and 15× on members-big, where the number of applicability tests falls from 4 million to 1,000. When extorder is enabled, this technique is redundant: extorder skips the same extensions unconditionally, at the price of changing the outcome of some cyclic programs. memberskip is the result-preserving alternative.
Cost
A cache per extension.

Indexing traits by member name

traitindex
Method
A qualified lookup T.m considers only the visible traits that declare a member named m, in their original order.
Correctness
A trait without such a member contributes no candidate, and examining it has no side effect.
Effect
About 6% on the standard library; larger with many traits in scope.
Cost
One table per scope.

Soundness fixes

The changes in this section alter results by design. Each addresses a case in which the existing implementation accepts an ill-typed program, terminates abnormally, or yields a result that depends on the order of declarations. None alters the output on the test suite.

1. Spurious equality derivations

fun g<T, U where T == U>() {}
fun f<V, W, D where V == W>() { g<D, V>() }   // accepted, although D == V does not follow

Cause. When a match succeeds only up to a coercion, the implementation assumes equalities between the mismatching subterms, but discards the bindings of unification variables made during the match. Subsequent steps may rebind those variables differently. The assumed equalities are then discharged for terms other than those compared, which yields a derivation of D == V from the unrelated fact V == W.

Fix fixsubst. The bindings are retained. Correct derivations of equalities are longer than the spurious ones, so this fix is viable only together with the decision procedure for equalities.

2. Exponential and depth-bounded equality derivations

fun f<T0, T1, T2, T3 where T0 == T1, T1 == T2, T2 == T3, T0 is P>(x: T3.X) { … }

Cause. A derivation of T0 == T3 by symmetry and transitivity requires about two steps per link, and the number of alternatives explored grows exponentially with the length of the chain. With more than four links, the depth bound is exceeded and valid programs are rejected.

Fix eqsolve, eqmgu. Closed equalities are decided by congruence closure, and open equalities of the form A ~ ?u are solved by their most general unifier.

3. Unreduced projections through pending requirements

extension <T where T is Collection, T.Element == Flag> Box<T> { fun first() -> Flag { … } }
fun g<T where T is Collection, T.Element == Flag>(b: Box<T>) { let f: Flag = b.first() }

Cause. The requirements of the extension are discharged in reverse order. When T.Element == Flag is discharged, its projection T.Element is qualified by the extension's own requirement T is Collection, which has not yet been discharged. No rule relates that projection to the caller's T.Element, so the equality is found only by an expensive search (1.4 s here), or not at all.

Fix eqsolve. The pending requirement is resolved in advance, in the environment in which it will later be discharged. The projection is identified with the corresponding projection of the caller only under two conditions: the resolution has a unique result, and every type involved is closed. Since resolution is deterministic, that result is the witness eventually used. Otherwise no refutation is drawn from the projection, and the search decides as before. Other forms of the problem remain open (see Limitations).

4. Cyclic bindings

given <U> => U is P<U> {}
given <T where T is P<S<T>>> => T is R {}
public fun main() { needR() }   // binds ?y := S<?y>; the compiler overflows its stack

Cause. Unification performs no occurs check. In addition, the variables of a function type's environment and those of method bundles were not reported by the predicate that tests whether a type contains unification variables.

Fix occurs, arrowenv. Cyclic bindings are rejected[9, 10]. The check covers every kind of type and runs in time linear in the size of the shared term. An occurs failure at the root of a match is treated as a mismatch; without this, it was treated as a successful match.

5. Dependence on the order of declarations

given T is P { type Y = U }
given U is Q { type O = T }
given Z.O is P { type Y = Int }   // accepted…
type Z = T.Y                      // …but rejected if these two declarations are exchanged

Cause. While the type of a declaration is being computed, the declaration is hidden from lookups, to prevent infinite regress. The answers of those lookups are memoized, but it is never verified that the hidden declaration would not have changed them. The outcome therefore depends on which declaration is computed first. Extensions whose extended types depend on members of other extensions exhibit the same problem. This is an instance of the general difficulty of scheduling name resolution soundly in type checkers[11].

Fix givencheck, extorder. Every lookup that omitted a hidden declaration is recorded, together with its query and the hypotheses in force. Once the types of all declarations involved are known, each record is checked: if the omitted declaration could have contributed a candidate, the program is reported as circular. For extensions, the check ranges over all lookups made by the members of a dependency cycle. If no omitted declaration could have contributed, the program is accepted with its original meaning.

Residual order dependence. The fix reduces the problem but does not eliminate it. Under declaration-order fuzzing (up to 24 permutations of the top-level declarations of each of 129 programs constructed for this problem), the verdict of the existing implementation varies with the order for 52 programs, and that of the revised implementation for 7. The remaining cases are cycles that pass through a type alias, or through a given and an extension together; the checks added here are specific to one kind of declaration each and do not observe such cycles from every entry point.

Context independence of the equality procedure

A goal may be posed under different hypotheses, in different instantiations, and at different points of the evaluation order. A decision procedure must not depend on these circumstances. Three rules ensure this.

  • Associated types of Self. Two rules of the language conflict:
    • the trait's abstract associated type Self.X is equal to T.X when T == Self;
    • projections T.X and U.X obtained through distinct conformances are distinct, even when T == U.
    Applying the first rule unrestrictedly yields T.X == Self.X == U.X under T == Self and U == Self, which contradicts the second. The procedure therefore equates Self.X with T.X only when the scope contains exactly one conformance to the trait for a type equal to Self. The condition is evaluated over the declarations of the scope alone, never over the goal or the hypotheses. The resulting theory is thus a fixed set of axioms per scope, and it is monotone: additional hypotheses never retract a conclusion.
  • Pending requirements (problem 3) are resolved in advance only in closed environments. A refutation that depends on an unresolved projection is not trusted.
  • Hypotheses are used as facts only within the derivation that introduced them, and each must itself be derived before that derivation is accepted.

Resource bound

Some searches remain exponential: those that the abstract model cannot refute, because a fact exceeds the truncation depth and the givens branch. Previously they exhausted memory. With budget, a resolution whose frontier exceeds 100,000 alternatives is abandoned, and the checker reports an error. Reporting is essential: a silently failed resolution could otherwise steer overload or extension selection towards a different candidate.

Rejected approaches

The following approaches improve performance but are not result-preserving, and are therefore not adopted.

ApproachReason for rejection
Unconditionally skipping extensions that do not declare the requested nameApplicability tests have side effects on which later lookups depend (problem 5). Skipping them changed results on programs with interdependent extensions. The restricted form described above is result-preserving.
Pruning goals that repeat an ancestor (loop checking)The classical argument[12] assumes SLD resolution. Here, pending premises act as hypotheses, so a repeated goal can be cheaper than its ancestor. Pruning altered the selected derivations, lost derivations within the depth bound, and concealed ambiguities.
Deferring overloaded calls and branching on the most constrained firstThe order in which overloads are explored and ranked determines which solution is preferred and which ambiguities are reported. Altering it changed acceptance in both directions.
Refuting equalities by equivalence classes without congruenceRejects valid programs in which Self.X equals T.X through the trait.
Rolling back all results computed during a cyclic lookupAccepted a program that is ambiguous under the checker's own rules, remained order-dependent, and incurred repeated recomputation.
Memoizing coercion queries under hypothesesResult-preserving, but without measurable benefit.

Limitations

  • Return-type overloading. A call g(h(), h(), …) in which h is overloaded on its return type takes time exponential in the number of arguments (8 s for nine arguments). A remedy would prune candidates without altering the order in which the solver ranks them.
  • Mutually recursive extensions. Extensions whose extended types depend on each other's members are reported as circular, even when only one interpretation is consistent: 
    extension A.Inner.Foo { type Inner = Bool }   // requires Foo, declared by the next extension
extension A.Inner { type Foo = Int }          // requires Inner in A, which the first might declare
    The existing implementation accepts this program only under a favourable evaluation order. Accepting it under every order would require a fixed-point computation over memoized results.
  • Residual order dependence. Dependency cycles through type aliases, and through givens combined with extensions, are still detected from some entry points only (7 of 129 fuzzed programs). Cycle detection is tied to the evaluation stack and to one kind of declaration at a time; a uniform treatment requires either explicit dependency tracking or a language rule that excludes such dependencies.
  • Resource bound. With the soundness fixes alone, a few valid programs with divergent givens exceed the bound. With the abstract model enabled, none of the test programs does.
  • Residual search. Equality goals containing unification variables inside types, such as Box<?v> ~ C, are still solved by search, as are projections through pending requirements of more complex forms.

Validation

  • Output equivalence. A semantic dump records every inferred type, name binding, conformance table and diagnostic, together with the witness selected at each elaborated site (coercions and implicit arguments; 11,817 sites). On the 192 tests and 24 workloads, the dump is identical to that of the existing implementation up to the terms of equality proofs, both with the soundness fixes alone and with all techniques enabled. Equality proofs differ in two files, where the decision procedure constructs them differently; they carry no computational content.
  • Declaration-order fuzzing. For 704 programs, up to 24 permutations of the top-level declarations were checked (11,554 runs). Outside the programs constructed for problem 5, no verdict depends on the order. Within them, 7 of 129 do (52 for the existing implementation).
  • Adversarial programs. A corpus of 520 programs was constructed to falsify the correctness argument of each technique. It targets unsound acceptance, abnormal termination, order dependence and pathological running times. Each reported defect was reproduced before being fixed.
    • On this corpus, the existing implementation terminates abnormally on 21 programs and exceeds a 30 s limit on 43.
    • The revised implementation terminates abnormally on none and exceeds the limit on one, a case of return-type overloading.
    • Every change of verdict falls into one of three groups: an ill-typed program now rejected; an abnormal termination or timeout now resolved; or the mutually recursive extensions discussed above.
  • Correctness arguments. Each technique is accompanied by an argument for its correctness, summarized above and given in full in the accompanying documents.

Threats to validity

  • The correctness arguments are informal; none is mechanized.
  • Output equivalence is established on a finite corpus. The adversarial programs complement it, but cannot exclude untested interactions.
  • The compiler's test suite barely exercises the soundness fixes: the equality procedure runs in 4 of the 216 files and refutes nothing there, and the cycle checks never run. Their validation rests on the adversarial programs, whose expected verdicts were established within this work and not against an independent specification.
  • Most stress workloads are synthetic, designed to isolate one cost. Their speed-ups indicate the asymptotic effect of a technique, not its effect on typical code, for which the standard library is the best available indicator.
  • Timings come from a single virtual machine. Repeated sessions differ by up to 20%, so the constant-factor techniques cannot be ranked reliably, and small differences are not significant.

Using the implementation

The implementation is a series of thirteen patches to the Hylo front end (patches/ in the accompanying archive). Each technique is enabled through the environment variable HYLO_TC_EXPERIMENTS:

Soundness fixes: occurs,fixsubst,eqsolve,extorder,arrowenv,eqmgu,givencheck,budget
All techniques (recommended): the above, together with symindex,coesrc,traitindex,memberskip,unify,index,absmodel,absquotient,typevec,reifymemo

The soundness fixes must be adopted together: fixsubst requires occurs, without which cyclic bindings cause abnormal termination, and eqsolve, without which equality chains exceed the depth bound.

Related work

Resolution as logic programming. Viewed as Horn clauses, givens make resolution a form of proof search. For propositional clauses, derivability is decidable in linear time[13, 14]; with variables, it is undecidable in general. The abstract model adopts the depth-k abstraction of Sato and Tamaki[1], one of several finite approximations of the success set of a logic program[15, 16, 17, 18, 19]. Non-failure analysis[20] is the closest precedent for using such approximations to establish that a call cannot succeed. The rejected loop check derives from the analysis of loop-checking mechanisms by Bol, Apt and Klop[12], whose soundness results presuppose plain SLD resolution.
Minimal derivations. Selecting the derivation of least cost, and reporting ties, is an instance of Knuth's generalization of shortest paths to grammars[5], subsequently formulated as weighted deduction[6, 21]. The counting of ties corresponds to semiring parsing[22].
Type-class resolution in other languages.
  • Repeated and cyclic subgoals: Lean 4 handles them by tabling[23], and the next-generation Rust trait solver by canonical-goal caching and fixed-point iteration[24].
  • Divergence: Scala 3 and GHC address it with termination conditions[25, 26]; the resource bound adopted here is a weaker alternative.
  • Coherence: the requirement that equally ranked derivations denote equivalent programs has been studied by Bottu et al.[27] and in the COCHIS calculus[28]. Quantified constraints[29] explain why generic equality givens defeat first-order models.
  • Type equivalence: Swift decides it by Knuth–Bendix completion of a rewriting system[30], an alternative to the congruence closure used here.
Equational reasoning. The equality procedure rests on congruence closure[2, 3] and union-find[4]. Its scope reflects known complexity results: rigid E-unification is NP-complete[7], and the word problem for general equational theories is undecidable[8]. The occurs check is part of syntactic unification from its inception[9, 10].
Indexing. Partitioning givens by head constructor is the first level of discrimination-tree and substitution-tree indexing[31, 32], as used for instance selection in Lean[33] and GHC[26].
Overload resolution. Overload resolution is NP-complete in general[34]. Polynomial algorithms exist for restricted settings such as Ada[35], and techniques from constraint satisfaction[36] prune the search in practice. Swift's solver combines a constraint graph with the pruning of disjunctions[37]. Bidirectional type checking[38] offers a complementary means of reducing the number of candidates by propagating expected types.
Name resolution and scheduling. Problem 5 is an instance of answering a name-resolution query before all information that bears on it is available. Scope graphs provide a formal account of name resolution[39, 40], and subsequent work gives criteria under which a query may be answered soundly[11, 41]. It also shows how resolution queries can be specialized for performance[42] and scaled to large code bases[43]. The memoization arguments for memberskip and coesrc follow the build-system view of incremental computation[44, 45].
