## dtree (effort M, risk medium)

Replace the head-only given index with a two-level discrimination index keyed by (trait or nominal head, rigid head of the Self argument). Make it independent of the typing stack: build it once and filter out on-stack givens when a query runs, recomputing group offsets at that point. Use the index's list of coercion sources to answer canDeriveCoercions in O(#sources) instead of scanning every visible given.

- **code locations:** Typer.swift:3631-3685 summon(_:in:where:then:penalties:ancestors:) (unindexed path 3660-3684); 3870-3918 GivenIndex and nominalHead; 3922-3960 givenIndex(visibleFrom:) (the restriction to an empty stack at 3923-3926 and 3956 is what disables the index during conformance checking); 4044-4097 indexedSummon (template; preconditions 4059-4069); 4246-4289 canDeriveCoercions (source selection 4268-4273, scan 4274-4282); 4298-4337 canDeriveCoercion(_:applying:) (returns 0b00 for every given that is not a source); 4130-4154 givens(visibleFrom:) (empty groups are dropped, so group offsets change with the stack); 565-582 anonymousImplementation (pushes d at 571); 5272-5281 notOnStack. New flag in TyperCounters.swift (TyperExperiments). Optional companion flag (absindex): AbstractResolution.swift:117-128 mayDerive scans a whole bucket linearly, and 223-231 insert does an O(bucket) subsumption check plus a copy-on-write copy of the bucket on every append.
- **profile evidence:** allon.txt (stdlib, all six flags on): canDeriveCoercions 12.63% inclusive (12.32% via Typer.match); 8.00% of it sits under anonymousImplementation, where d is on the stack and the index is unavailable. Its callee canDeriveCoercion(_:applying:) takes 9.59% (the full scan: contextAndHead 2.61%, declaredType 2.22%, Dictionary.find 2.1%), and givens(visibleFrom:) under canDeriveCoercions takes 1.53%, a sign of the fallback path. The unindexed summon path costs formThread 1.61% plus expression(referringTo:) 1.23%. Counters (stdlib, all on): index.unavailable=888, index.fallback=35, summon.matches=3541 vs matchOK=266, summon.subgoals=291. breadth80: summon.matches=6480 for 80 subgoals, with matchOK=160, i.e. 79 of every 81 threads in the P_i bucket fail on a Self mismatch (A_j vs A_k). takeSummonResults 16.13%, match 15.84%, canDeriveCoercions 6.47%, coerced 10.08% (the same fan-out). absmodel side: mayDerive 5.87% on breadth80 with 6463 facts and 0 refutations.
- **expected gain:** stdlib typing: about -12 to -16%. canDeriveCoercions drops from 12.6% to under 1%, and the unindexed fan-out plus failing matches (about 3-4%) mostly disappear (roughly 160 -> 137 ms). breadth80 user typing: about -20 to -30% (6480 -> ~160 matches; the takeSummonResults and coerced share of ~16% becomes negligible). Another ~5% with the absindex companion when absmodel is on. members-big: about -3% (summon 8%). ovl-8-8 and ovr-3-10: only the stdlib part benefits (their user typing is ~5 ms).
- **soundness:** There are three parts, and each keeps exactly what the baseline (no index) computes. (a) Coercion sources: canDeriveCoercion returns 0b00 for every given whose head is neither a bare quantified parameter nor T ~ U. Skipping those givens therefore leaves the OR accumulator unchanged, and the early exit happens at the same source (the given that first makes the result 0b11 is necessarily a source). The memo writes are the same except for the 0b00 entries of non-sources, which are pure caches. To keep the order of declaredType side effects identical, the stack-independent index is built only when the baseline would itself compute every visible not-on-stack given's type: on an empty stack (as `index` does), as a by-product of a canDeriveCoercions scan that ran to the end, or in summon(where:), which forms a thread for every visible given. On-stack givens whose type is not memoized yet are recorded as `missing`, and the index is reused only while missing ⊆ stack. (b) Stack filtering: entries are filtered by notOnStack, and the group offset of each entry is recomputed as the rank of its raw group among the raw groups that still have a member left. That reproduces `if !ls.isEmpty { gs.append(ls) }` exactly. Built-in givens get a + survivingGroupCount, so penalties are unchanged. (c) The second level is used only under the existing `index` preconditions: no source left after filtering, and no assumed equality in the environment. Take a given concluding P<Self=X> against the goal P<Self=Y>, where X and Y have different rigid heads (different nominal declaration or machine type, or a different rigid GenericParameter; GenericParameter vs GenericParameter is false at TypeStore.swift:1040-1041). unifiable reaches (X,Y), unifiableSameShape returns false, and the coercion handler records (X,Y). That pair is not (a,b), so match calls canDeriveCoercions, which returns false, and the thread dies with .next([]) (Typer.swift:3776-3781) in the layer where it was spawned. Omitting it changes neither the results nor the BFS layering. Variables, the given's own quantified parameters (after opening), associated types, tuples, arrows, metatypes and remote types are wildcards on both sides. Aliases are dealiased, as nominalHead already does. The only remaining difference is fresh-variable numbering, which `index` already perturbs.
- **overlaps with:** Supersedes `index` entirely: with dtree on, `index` becomes unnecessary because dtree has its own index, works with a non-empty stack, and adds the second level. On the stdlib it also takes most of the benefit of `absmodel` (its 104 refuted subgoals would get 0 or 1 candidate thread here). Independent of names, unify, solver and loopcheck. The absindex companion only matters when absmodel is on.
- **implementation sketch:** 1) Add `struct GivenIndex2 { byKey: [Key2: [Entry]]; byHead: [K: [Entry]]; wildcards; all; sources: [Entry]; rawGroupSizes: [Int]; positionsOf: [DeclarationIdentity: [Int]]; missing: Set<Given> }` with Key2 = (head, rigidSelfHead?), plus a cache `scopeToGivenIndex2`. 2) build(scope): enumerate the groups the way givens(visibleFrom:) does, but without notOnStack. For each given g: if it is on the stack and its type is not memoized, add it to missing; otherwise call declaredType(g), contextAndHead, and seenAsTraitApplication(head) to get arguments.values[0], then compute rigidKey (nil if it is one of the context parameters). 3) view(stack): compute removed[rawGroup] from the stack via positionsOf (O(|stack|)), then offset[rawGroup] = number of earlier groups that keep a member. 4) In summon(where:), when the flag is on: env givens as today; then the candidates for (nominalHead(u), rigidKey(selfArg(u))) are byKey bucket ∪ second-level wildcards ∪ wildcards, merged by position and filtered by notOnStack, with penalty = base + a + offset[group]; built-ins as in indexedSummon. Fall back to the old path if the filtered sources are non-empty or an assumed equality exists. 5) In canDeriveCoercions, replace `sources` with view.sources.filter(notOnStack) when a complete index is cached. Otherwise run the original scan and, if it ends without an early exit, store the classification. 6) absindex: key facts by (head, first-argument key), keep a Set<Term> for ground duplicates, and mutate buckets in place (facts[k, default: []].append).

## symindex (effort S, risk low)

Build the standard-library symbol table in a single pass over the stdlib syntax (an inverted index from @_symbol string to nodes), instead of running one full select(from:.symbol(name)) scan per StandardLibraryEntity (24 scans, each doing an `as? any Annotatable` existential cast on every node).

- **code locations:** Program.swift:2004-2018 initializeStandardLibraryCaches (called from Typer.swift:40-42 on every stdlib typing, and from Program.swift:2075-2077 every time the stdlib is loaded from an archive); Program.swift:2102-2106 select(from:_:); 2141-2142 SyntaxFilter .symbol; 1458-1462 symbol(annotating:); 1651-1662 annotations/annotation (the `as? any Annotatable` cast).
- **profile evidence:** allon.txt: Program.initializeStandardLibraryCaches 13.70% inclusive -> Sequence.filter 13.35% -> SyntaxFilter.callAsFunction 13.07% -> Program.symbol(annotating:) 12.94% -> annotations 12.27%. It is a large part of the 18% swift_dynamicCast/tryCast inclusive. Same share in ovl-8-8 (13.97%) and ovr-3-10 (12.92%). 24 entities (Program.swift:1872-2003) means 24 passes over all stdlib nodes.
- **expected gain:** About -13% of stdlib typing (13.7% x 23/24, roughly 20 ms of 160 ms), and the same absolute saving in every compilation that loads a prebuilt stdlib archive. Stress workloads gain the same constant (around 20 ms) because they type the stdlib too.
- **soundness:** Exact. The single pass visits modules.values[m].syntax in the same order and appends each node n with symbol(annotating:n) == s to table[s]. For each entity, table[name]?.uniqueElement is the same as select(from:a,.symbol(name)).uniqueElement, because filter preserves order and the predicate is identical. castToDeclaration and the precondition on a missing or duplicate symbol behave identically. There are no other side effects.
- **overlaps with:** None of the six flags. It also lowers the swift_dynamicCast share that the `unify` and representation work target.
- **implementation sketch:** if TyperExperiments.symindex { var t: [String: [AnySyntaxIdentity]] = [:]; for n in modules.values[a].syntax { if let s = symbol(annotating: n) { t[s, default: []].append(n) } }; for e in StandardLibraryEntity.allCases { guard let b = t[e.rawValue]?.uniqueElement, let d = castToDeclaration(b) else { precondition(allowPartialStandardLibrary, ...); continue }; standardLibraryDeclarations[e] = d } } else { old loop }. Optionally skip nodes whose tag is not a declaration before the existential cast.

## memberindex (effort S, risk low)

Index the scope graph's extension and trait edges by member identifier, as an inverted index from identifier to the extensions and traits that declare a member with that identifier, kept in visibility order. A member query then visits only the edges that carry its label, instead of probing every visible extension and every visible trait.

- **code locations:** Typer.swift:4665-4671 resolve(_:memberInExtensionOf:...); 4675-4708 resolve<S>(_:declaredIn:applyingTo:...) (the `names` filter at 4683 and the per-extension declarationsOnStack lookup at 4681); 4903-4939 extensions(visibleFrom:) / extensions(visibleAtTopLevelOf:) (the per-scope arrays are concatenated at 4912-4914); 4819-4831 lookup(_:memberOfTraitVisibleFrom:); 5035-5061 traits(visibleFrom:); Memos at 76-85 (add scopeToExtensionsByName and scopeToTraitsByName).
- **profile evidence:** members-big.txt: specialized resolve<A>(declaredIn:applyingTo:) 40.92% inclusive. Its callees are Dictionary.find 15.73% (declarations(lexicallyIn:) lookups plus the declarationsOnStack Set probe for every extension), swift_retain 8.46%, swift_release 7.76% and self 3.26%. Counters: names.skippedExtensions=4,007,000 vs names.appliesCalls=1000, i.e. about 4000 extension visits per member lookup (init plus m). stdlib (allon.txt): lookup(_:memberOfTraitVisibleFrom:) 3.78%, of which 2.64% is copying and destroying the Typer value for the `filter(resolvableWithQualification(_:))` closure, run for every trait even when the trait does not declare the name. resolve(declaredIn:) is 0.54%.
- **expected gain:** members-big user typing: about -55 to -65% (about 2.5x; resolve(declaredIn:) goes from 41% of all samples to under 1%). members (500 extensions) shows the same ratio. stdlib: about -3 to -4%. breadth80, ovl and ovr: negligible.
- **soundness:** For extensions, the per-identifier list is the visible-extension array filtered by declarations(lexicallyIn:e)[n.identifier] != nil, in the original order. The per-name list of a nested scope is the parent's list followed by the local list, mirroring 4912-4914. The loop then runs the same declarationsOnStack check and the same applies, and produces candidates exactly as `names` does. Compared with the baseline without `names`, skipping applies for extensions that do not declare n is justified by the argument already accepted for `names`: such an extension contributes no candidate, and applies only fills scopeToExtensionApplies and types the extendee, which happens anyway when the extension is checked. For traits, a trait that does not declare the identifier yields an empty ms and is skipped by the baseline (4826), so iterating only the hits and still applying lookup(name, lexicallyIn:) (with refineLookupResults) plus the resolvableWithQualification filter gives an identical result. Both indexes key on the identifier only, and label or introducer refinement still runs on the hits.
- **overlaps with:** Subsumes `names`, which becomes unnecessary when memberindex is on. Independent of index, unify, absmodel, solver, loopcheck and dtree. A possible step 3 is a second key on the extendee's nominal head (lit-solver-names B2.3); it would only matter when many extensions declare the same name.
- **implementation sketch:** 1) extensionsByName(visibleFrom s) -> [String: [ExtensionDeclaration.ID]], with the same recursion as extensions(visibleFrom:): at the top level, iterate extensions(visibleAtTopLevelOf:) and, for each e, for each key of declarations(lexicallyIn:.init(node:e)), append e. In a nested scope, take a copy of the parent's map and append the local extensions. Cache by scope or by file offset. 2) In resolve(memberInExtensionOf:), when the flag is on, pass extensionsByName(...)[n.identifier] ?? [] to resolve(declaredIn:) (and skip the `names` check, which is now redundant). 3) traitsByName(visibleFrom:) built the same way from traits(visibleFrom:). In lookup(memberOfTraitVisibleFrom:), iterate traitsByName[name.identifier] ?? [] and apply the existing body. 4) Counter: memberindex.visited.

## probereuse (effort S, risk medium)

In the forward-checking solver, keep the forked state of each probe. When the solver later branches on (or commits to) a candidate, it resumes that candidate's probe fork, which has already been propagated to quiescence, instead of forking again and repeating the same propagation. A follow-up (components) splits the parked overload sets that remain ambiguous into connected components of the variable-constraint graph, so their search costs add up instead of multiplying.

- **code locations:** Solver.swift:594-630 resolveParked (the commit at 621-627 re-inserts the equality and re-propagates); 634-645 probe (its fork is discarded at 643-644); 654-706 solve(overload:among:) (forks again at 667-673); 96-183 solution(betterThanOrEqualTo:using:) (probe stop at 106-108, cancel test at 161).
- **profile evidence:** stdlib counters (all on): solver.probes=338, solver.forks=316, solver.prunedChoices=0, and no solver.commits. Every probed choice is therefore propagated twice: once in the probe and again from scratch in its fork. Solver.probe is 2.81% inclusive of stdlib; resolveParked is 5.37%. ovl-8-8: 64 probes and 8 commits (each commit re-runs the survivor's propagation). ovr-3-10: 30 probes and 10 commits.
- **expected gain:** stdlib: about -2 to -2.5% (the duplicated probe work). ovl-8-8 and ovr-3-10 user typing: about -10% (a few ms in absolute terms). Components: no gain on the current workloads (none has two or more independent sets that each keep two or more zero-error survivors). The asymptotic gain, from a product of domain sizes to their sum, would appear with generic-vs-concrete or ranking-only overloads that probing cannot prune.
- **soundness:** A probe fork and the baseline branch fork start from identical solver states: same goals, outcomes and stale set, fresh empty, parked minus g, outcomes[g] = delegate([equality]), and bindings[k.name] = choice. Both run the same deterministic loop until fresh is empty, and the probe stops exactly at that point (106-108), before resolveParked and the coercion/widening refresh. Two parameters can differ. The first is `best`, which may have tightened between the probe and the fork. Because current.errors only increases (line 159 is the only writer of current), 'canceled at some step under the tighter best' is equivalent to 'fork.current > me.best at resume', so resumption returns nil in that case and the outcome is the same. The second is the probing and best properties, which are reset (probing=false, best=me.best) before the loop resumes. What remains different is fresh-variable numbering and cache contents, which `solver` already perturbs. For components, the per-set isPreferred selection and the additive error score let independent components be solved separately and merged, but the ambiguity-diagnostic placement and the `best` pruning need a proof, so that part is medium risk. The flag is a no-op when `solver` is off.
- **overlaps with:** A refinement of `solver`; it does nothing without it. No overlap with the other flags.
- **implementation sketch:** In resolveParked, keep `forks: [GoalIdentity: [(NameResolutionCandidate, Solver)]]` for the probes that finished with 0 errors, for the selected set only. For a commit, if a stored fork exists for the survivor: `var f = stored; f.probing = false; f.probeFinished = false; f.best = best; self = f with typer reattached; return .running`. In solve(overload:among:), when a stored fork exists for the choice, return nil if f.current > me.best; otherwise set f.best = me.best and call f.solution(betterThanOrEqualTo: me.best, using: &me.typer). Components (later): build a variable-to-goal adjacency over parked plus stale goals, compute union-find components, solve each component as a separate Solver, and merge substitutions, bindings and diagnostics.

## knuthtable (effort L, risk high, SEMANTIC CHANGE)

SEMANTIC CHANGE: replace the lock-step BFS with its maxImplicitDepth=10 step cap by tabled resolution in Knuth order. Each subgoal (α-normalized reified goal, scope, multiset of assumed givens) gets one table entry, and the agenda is a bucket queue on (steps, penalties). A size-based bound or absmodel/loopcheck guarantees termination. A sound sub-flag, hcap, keeps the cap and only predicts depth-cap failures: it computes the exact minimum derivation height of the goal on the goal-instantiated ground hypergraph (with bounded expansion) and returns [] immediately when that height exceeds the cap.

- **code locations:** Typer.swift:24 maxImplicitDepth; 3841-3865 takeSummonResults (BFS loop and cap); 3631-3685 summon(where:) (pending assumed givens are candidates, 3663); 3794-3817 threadContinuation (premises are solved sequentially); 3590-3621 summon memo rules. hcap hooks into summon(_:in:) before 3611.
- **profile evidence:** Workloads: chain9 and chain12 fail with summon.depthExhausted=1 or 2 and the diagnostic "no coercion from 'P<S^9<Z>> ==> ...'", although the derivation is finite and unique (chain8 passes). User typing is 18 ms for chain9 vs 4.7 ms for chain8. stdlib: summon.layers=227 for 3071 summon calls and summon.depthExhausted=0, so on the stdlib this is about semantics, not speed (summon search excluding canDeriveCoercions is about 11% and is not dominated by repeated subgoals).
- **expected gain:** knuthtable: accepts valid programs whose proofs need more than 10 steps (finding 1 of REPORT §6). It is exponential-to-polynomial on diamond-shaped or repeated subgoals (Lean 4 tabling), but no current workload has diamonds, and the stdlib gain is about 0%. hcap (sound): chain9 and chain12 user typing goes from about 9-18 ms to about 1-2 ms; stdlib about 0%.
- **soundness:** knuthtable is a semantic change. It removes the step cap, so programs that are rejected today are accepted, and its termination relies on a term-size bound (Lean's bounded term-size assumption) or on absmodel. To stay close to today's results it has to (i) order the agenda by (steps, Σpenalty), (ii) keep every answer of minimal cost, so that ambiguity is still detected, and (iii) model or respecify the sharing through pending premises (3663), which can make the step count smaller than the tree size. Keep it separate and run differential tests. hcap is sound. A completed thread's BFS layer is at least the height of its derivation: each path from the root to a leaf passes through distinct match steps, and sharing through a pending premise saves size but not height, since every node costs at least 1. So if the exact minimum height h*(goal) > maxImplicitDepth, no thread completes before the cap and takeSummonResults returns []. Note that the depth-k abstract model cannot supply this bound, because truncation collapses S^n chains to height ≤ k+1. hcap therefore needs a top-down unfolding of the ground goal (Liu–Smolka local fixpoint with Knuth 1+max), and bails out to 'unknown' when the unfolding meets variables, coercion sources, or more than N nodes.
- **overlaps with:** knuthtable subsumes loopcheck (variant loops become shared table entries) and overlaps with absmodel for divergence (absmodel is still needed for growing terms unless a size bound is used). hcap complements absmodel (which cannot bound height) and is orthogonal to index, dtree and names.
- **implementation sketch:** hcap: in summon(_:in:), for a closed goal t with no coercion source visible, run h(t) = 1 + max over premises of h(premise), minimized over candidate givens from the index (ground instantiation through unifiable). Memoize per (scope, t), use an in-progress marker equal to infinity for cycles, and stop at 64 nodes, returning unknown. If h(t) > maxImplicitDepth, return []. knuthtable: a Table [Key: Entry{answers, consumers}] keyed by canonicalized reify(t), plus a bucket queue indexed by step count. A generator forms threads for a goal once, and consumers resume on answers in cost order. Stop when the root's minimal-cost bucket is final, and return all its answers.
